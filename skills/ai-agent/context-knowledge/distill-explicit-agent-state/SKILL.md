# 可审计的显式状态蒸馏

## R — 原文 (Reading)

> 这种机制的本质是把分散在上下文各处的隐式状态提炼为可直接使用的显式知识。
>
> — 李博杰，第 2 章 2.6.1「Agent 状态栏的理论基础」，PDF 第 68 页（书内第 60 页）

---

## I — 方法论骨架 (Interpretation)

长轨迹把当前状态隐含在许多消息、工具调用和时间点里。每轮让模型重新数次数、找待办和判断最新版本，不但浪费推理，还会把确定性状态计算变成概率任务。

状态蒸馏用运行时代码把事件流归约成一个小型结构化投影：当前进度、完成项、待办、预算、工具计数、pending 任务、锁、时间与异常。投影放在动态上下文末端，便于当前决策直接读取；原始轨迹仍是权威证据，状态栏不能替代它。

关键约束有三条：状态只由有明确语义的事件更新；每个字段带版本或来源；状态准确率和轨迹一致性要被持续验证。因为模型会高度信任显式字段，错误状态栏比没有状态栏更危险。

## A1 — 书中的应用 (Past Application)

### 案例 1：状态栏把长历史统计变成常量查询（c011）
- **问题**：退款客服长轨迹中，模型需要反复从历史统计工具次数、进度、TODO 和时间，弱模型尤其容易算错。
- **方法论的使用**：作者用短代码维护时间戳、工具计数、TODO 等五种状态，并把结构化摘要放到当前决策附近。
- **结论**：状态检索应由确定性运行时预计算，模型只消费结果；用 LLM 批量维护反而不可靠。
- **结果**：弱模型准确率提高 40-54 个百分点；强模型的思考量、延迟和花费约下降一个数量级。

### 案例 2：异步 Agent 的 pending 状态（c031）
- **问题**：同步模型被异步事件打断时，等待占位符可能被误读为真实结果，原任务也可能被遗忘。
- **方法论的使用**：运行时分离启动、pending、事件到达和完成状态，并在循环安全点更新任务 ID 与状态。
- **结论**：异步占位符必须是显式状态而非伪造结果，恢复时要指向原任务。
- **结果**：系统能让新事件打断当前循环，同时保持未完成任务可恢复，不以占位文本代替真实完成信号。

## A2 — 触发场景 (Future Trigger)

### 用户会在什么情境下需要这个 skill?

1. Agent 跨几十轮跟踪进度、工具次数、预算或 TODO，每轮都重新读长历史。
2. 长任务在压缩、打断或恢复后重复执行已完成副作用。
3. 异步工具有 running/pending/completed/failed 多种状态，模型把占位符当结果。
4. 多个事件更新同一状态，系统无法判断哪个版本最新或状态来自哪里。

### 语言信号 (用户的话里出现这些就应激活)

- “给 Agent 做一个状态栏 / status bar”
- “不要让模型每轮重新数工具调用” / “explicit state instead of rescanning history”
- “pending job 被当成完成了” / “pending is mistaken for completed”
- “长任务恢复后又执行了一遍” / “duplicate action after resume”

### 与相邻 Skill 的区分

- 与 `build-evidence-backed-memory` 的区别：本 skill 维护当前任务的运行状态；后者管理跨会话事实、冲突和长期知识。
- 与 `design-cache-stable-context` 的区别：本 skill 计算状态内容；后者决定动态状态应放在稳定前缀之后。
- 与 `isolate-before-compressing-context` 的区别：状态栏是特定高价值投影；压缩/隔离治理的是整个上下文的信息量和噪声。
- 与 `engineer-agent-failure-closure` 的区别：本 Skill 从事件轨迹归约“现在是什么状态”；后者定义遇到失败后允许怎样转移、恢复和终止。
- 与 `design-realtime-agent-interactions` 的区别：本 Skill 生成权威状态投影；后者规定 partial/final/pending 事件何时可被下游消费和提交。

## E — 可执行步骤 (Execution)

当 skill 被激活后，agent 应按以下步骤执行：

1. **选择值得显式化的状态**
   - 找出模型反复从轨迹推导、会决定下一动作且可由事件确定计算的字段；排除主观判断和不稳定猜测。
   - 完成标准：每个字段都有消费方、更新事件和错误后果；没有“可能以后有用”的装饰字段。
   - 判停条件：任务短、字段无需跨轮或无法可靠计算时，不建立状态栏。

2. **定义状态 schema 与权威来源**
   - 为字段定义类型、初值、状态机、版本、来源事件、时间和不变量；明确原始轨迹/环境日志为 source of truth。
   - 完成标准：能区分 `pending`、`completed`、`failed`、`cancelled`，且每次副作用有稳定 ID。

3. **实现确定性 reducer**
   - 用代码按事件顺序更新状态；相同事件幂等，旧版本拒绝覆盖新版本，冲突进入异常字段而非由模型猜测。
   - 完成标准：同一事件序列重放得到完全相同状态，乱序、重复与缺失事件均有测试。

4. **把投影注入动态末端**
   - 使用短、固定 schema 的状态块放在当前上下文末端；携带更新时间和轨迹游标，不删除原始消息。
   - 完成标准：模型能直接读取当前值，并可按游标回查证据；状态变化不改系统前缀。

5. **验证状态-轨迹一致性**
   - 在线断言计数、任务状态、锁和预算不变量；抽样从原始轨迹重算，对差异告警并停止敏感动作。
   - 完成标准：状态准确率、延迟和差异率有监控，错误状态不能静默进入决策。
   - 判停条件：状态无法确认或与环境冲突时，以环境/原始日志为准，标记未知并转恢复流程。

6. **用长轨迹回归验收**
   - 比较有无状态栏的准确率、重复动作、思考 token、延迟和成本；覆盖压缩、打断、恢复和旧版本事件。
   - 完成标准：目标状态任务改善，普通对话不退化，原始证据仍完整可审计。

## B — 边界 (Boundary)

### 不要在以下情况使用此 skill

- 要保存用户偏好、历史政策或跨会话经验；这些是长期记忆/知识，不是当前运行状态。
- 字段依赖价值判断或开放式文本理解且没有可信验证，不能伪装成确定状态。
- 任务很短、状态可直接从当前工具结果读取，额外投影只增加维护成本。

### 作者在书中警告的失败模式

- **ce018 让 LLM 充当权威状态计算器**：确定性计数交给概率模型会累积漂移，且难以复现。
- **ce019 用有损状态摘要替换原始证据**：投影丢掉因果与来源，不能承担审计和重建。
- **ce020 追加式状态造成新旧版本歧义**：状态必须带版本、有效期和明确取最新规则。
- **ce050 把异步占位符误当真实结果**：`pending` 必须显式，不能满足格式就冒充完成。

### 作者的盲点 / 时代局限

- 书中状态栏实验偏工具调用和客服计数，不能直接外推到需要复杂语义理解的状态。
- 强模型、原生长记忆或新型上下文架构可能降低收益，但不会消除权威状态与审计要求。
- 复杂状态机本身会成为故障源；低风险短流程不应为了“生产感”过度设计。

### 容易混淆的邻近方法论

- 状态栏回答“现在任务处于什么状态”，记忆回答“过去有哪些可长期复用的事实”。
- 摘要追求减少信息量，状态蒸馏追求把特定确定性变量变成直接查询。
