# 隔离优先、压缩兜底的上下文治理

## R — 原文 (Reading)

> 压缩是有损的、需要额外 LLM 调用的事后补救；隔离则让噪声从一开始就与主上下文绝缘
>
> — 李博杰，第 2 章 2.7.7「隔离优于压缩：子 Agent 上下文隔离」，PDF 第 77 页（书内第 69 页）

---

## I — 方法论骨架 (Interpretation)

上下文窗口大小只是容量上限，不是有效注意力保证。未超限的长轨迹也会因重复、冲突和低价值中间过程出现上下文腐化。

治理顺序应是：先问哪些信息根本不应进入主上下文。搜索、解析、试错或并行探索如果主任务只需要其结论，应在隔离上下文完成，通过自包含移交包回传目标相关的产物、证据和未决项。只有无法隔离的共同状态，才进入压缩流程。

压缩是有损转换，必须按信息价值分层触发，而不是每轮重写。应优先删可重建噪声，归档大输出，再联合压缩相关证据；强制保留决策理由、不可变约束、验证状态、未决问题、失败路径和来源。压缩后还要验证任务是否能继续，而不是只检查 token 变少。

## A1 — 书中的应用 (Past Application)

### 案例 1：六种上下文压缩策略对比（c012）
- **问题**：128K 窗口中的长程职业状态追踪既会溢出，也会因逐项摘要产生重复和截断。
- **方法论的使用**：作者比较无压缩、个体摘要、组合摘要与任务感知策略，同时记录完成率、轮数和 token。
- **结论**：压缩单元必须与任务语义对齐；逐项摘要会碎片化，简单拼接又会截掉后部证据。
- **结果**：无压缩第五轮溢出；个体摘要 12 轮、276,608 token；组合摘要降至 10 轮、93,449 token，但仍有截断风险。

### 案例 2：十个网站并行搜索与级联终止（c096）
- **问题**：串行搜索十个网站会把每个站点的浏览中间过程全部压入管理者上下文。
- **方法论的使用**：Manager 为各网站创建隔离浏览器 Agent，只接收状态和带证据的结果；任一命中后级联终止其余任务。
- **结论**：独立探索轨迹无需汇入主上下文，主任务只需要可验证结果和生命周期状态。
- **结果**：图示案例从约五分钟缩短到十九秒，约 15 倍加速，同时显式处理并发命中与终止确认竞态。

## A2 — 触发场景 (Future Trigger)

### 用户会在什么情境下需要这个 skill?

1. 长会话未达到 token 上限，但 Agent 开始忽略早期约束、重复旧路径或工具误选。
2. 多路搜索、日志解析、代码探索产生大量中间信息，主任务实际只需要结论和证据。
3. 团队正选择滑窗、逐项摘要、全量摘要、归档或子 Agent 隔离方案。
4. 压缩后 Agent 忘记决策理由、失败尝试、验证状态或未决事项。

### 语言信号 (用户的话里出现这些就应激活)

- “上下文还没满，但 Agent 已经开始变笨” / “context rot before overflow”
- “应该压缩还是用子 Agent 隔离？” / “compression vs context isolation”
- “摘要后它又尝试了已经失败的方案” / “lost negative evidence after compaction”
- “多路研究怎么只回传必要结果？” / “self-contained handoff from parallel research”

### 与相邻 Skill 的区分

- 与 `design-cache-stable-context` 的区别：本 skill 管信息价值、噪声与容量；后者管稳定前缀的 token 复用。
- 与 `distill-explicit-agent-state` 的区别：本 skill 治理整条上下文；后者只为进度、计数等确定变量建立状态投影。
- 与 `design-multi-agent-collaboration` 的区别：本 skill 把隔离作为上下文治理手段；后者判断是否需要多 Agent 并设计协作拓扑。

## E — 可执行步骤 (Execution)

当 skill 被激活后，agent 应按以下步骤执行：

**执行硬门：** 在确认共享依赖并写出自包含的输入、输出与验收契约前，不得创建隔离上下文或子 Agent；只有“少回传日志”不构成可执行的移交包。

1. **建立信息流与腐化基线**
   - 标记上下文来源、体积、重复度、后续消费者和可重建性；记录成功率、约束遗忘、重复调用、token 与延迟随轮数的变化。
   - 完成标准：能指出哪些信息量增长与行为退化相关，不只报告窗口占用。

2. **优先识别隔离候选**
   - 选择中间过程庞大、与其他步骤共享状态少、主任务只需产物或结论的子任务；同时检查权限边界。
   - 完成标准：每个隔离任务都有明确输入、输出和不共享的私有轨迹。
   - 判停条件：若子任务依赖频繁共享的隐式状态，隔离会产生更高同步损失，保留在主上下文或先显式化接口。

3. **设计自包含移交包**
   - 包含目标、输入引用、已确认事实、约束、预算、输出协议、验收标准、证据路径和未决问题；大产物传引用而非全文。
   - 完成标准：接收方不读取父 Agent 私有轨迹也能正确开工，主任务能独立验证返回值。

4. **为剩余内容设置分层压缩阈值**
   - 依次采用删除可重建噪声、归档完整大输出、联合任务感知摘要、必要时全量重建；按批次触发，不每轮压缩。
   - 完成标准：触发条件同时考虑 token、注意力退化和行为指标，且每层有可逆来源。

5. **强制保留高价值字段**
   - 压缩模板至少保留目标、不可变约束、当前计划、决策理由、完成/失败验证、未决事项、失败路径、来源与恢复指针。
   - 完成标准：摘要中的每个关键结论可追溯到原始轨迹，失败证据不会因“负面”被删。

6. **做可继续性与成本验收**
   - 从压缩/移交后的上下文继续任务，测试能否复述约束、避免重复副作用、定位证据并完成下一步；比较完成率、轮数、token 与延迟。
   - 完成标准：上下文缩减达到目标，任务行为和审计性不退化。
   - 判停条件：若摘要丢失因果或隔离导致反复补背景，回滚并调整边界；不要继续摘要套摘要。

## B — 边界 (Boundary)

### 不要在以下情况使用此 skill

- 只有缓存 miss 或 TTFT 问题，没有上下文腐化；使用稳定前缀布局。
- 只是计数、TODO、pending 状态难取；先用确定性状态栏，不要摘要整段轨迹。
- 任务短且共享依赖密集，隔离和移交成本高于保留完整上下文。

### 作者在书中警告的失败模式

- **ce010 滑动窗口切掉关键任务状态**：新旧不等于价值，机械保留最近 N 条会丢失早期约束与确认。
- **ce021 等到溢出才治理上下文**：上下文腐化常先于 token 超限发生。
- **ce022 每轮压缩破坏缓存并累积失真**：递归重述同时提高成本和事实漂移。
- **ce023 逐项摘要制造碎片与重复**：压缩单元与任务语义不一致。
- **ce024 压缩时删除决策依据与失败路径**：只留结论会重开已证伪方案。
- **ce025 隔离子任务却不给自包含输入**：隔离也切断必要信息，移交包必须补足接口。

### 作者的盲点 / 时代局限

- 更长上下文和原生记忆模型会改变阈值，但不保证注意力质量；应以行为基线而非固定 token 数决策。
- 子 Agent 隔离会增加协调、权限和可观测性成本，中小团队不一定能维护完整运行时。
- 书中以软件、搜索和文件系统任务为主；高度互依的组织决策未必适合被拆成隔离子任务。

### 容易混淆的邻近方法论

- 隔离不是“把任务交给更多 Agent”；没有独立输入输出边界时，多 Agent 只会增加语义损失。
- 压缩不是知识沉淀；任务摘要可以临时有用，但未经跨轨迹验证不能晋升为长期经验。
