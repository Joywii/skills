# 能力缺口驱动的渐进式披露

## R — 原文 (Reading)

> 先给 Agent 看一份目录摘要，需要时再加载完整内容
>
> — 李博杰，第 2 章 2.5.1「Skills：领域能力的可组合单元」，PDF 第 63 页（书内第 55 页）

---

## I — 方法论骨架 (Interpretation)

大型能力库的问题不是“模型不知道全部能力”，而是每个决策点不应同时为全部细节付费。渐进披露把能力拆成三层：

1. **目录层**常驻少量名称、触发条件、禁用条件和风险摘要，负责可发现性。
2. **核心流程层**只在任务命中后加载，给出步骤、判停和验收。
3. **细则层**按执行中的具体需要读取脚本、模板、schema 或参考文档。

能力需求还会随中间观察展开，因此发现不应只发生在用户初始请求。Agent 在执行中识别“我缺少什么能力”，再分层匹配、加载、继续；低置信匹配应返回未找到，而不是强配一个相似工具。已加载内容应保持稳定引用和原位置，兼顾路由正确性与缓存复用。

## A1 — 书中的应用 (Past Application)

### 案例 1：按需加载 PPTX Skill（c009）
- **问题**：把所有文档处理规则、PPTX XML 细节和脚本启动时全塞入上下文，会浪费 token 并稀释注意力。
- **方法论的使用**：启动时只暴露 PPTX Skill 元数据；命中“从论文生成演示稿”后加载核心流程，再按实际步骤读取 html2pptx、参考规范和脚本。
- **结论**：目录负责路由，主 Skill 负责工作流，子文档与脚本只服务当前步骤。
- **结果**：实验验收目标是生成 10-15 页、主线完整、至少三张一致图表且可打开的演示稿；正文未给统一得分。

### 案例 2：小模型主动发现 120+ 工具（c032）
- **问题**：Qwen3-4B 一次看到 120+ 工具、50K+ token schema 时，错选并遗忘工具。
- **方法论的使用**：系统仅常驻基础工具和 `discover_tools`；Agent 遇到能力缺口后用自然语言检索 3-5 个候选并加载详细 schema。
- **结论**：执行中发现能力比开局按表面查询一次性预筛更能覆盖多步任务。
- **结果**：实验预期显著提升准确率与完成率，但书中未报告最终量化结果，不能把架构示意当实测数字。

## A2 — 触发场景 (Future Trigger)

### 用户会在什么情境下需要这个 skill?

1. Agent 有几十到上千个 Skill、工具或 MCP 服务，启动上下文很大且工具误选率上升。
2. 团队想设计 Skill 目录、插件市场或大型操作手册的按需加载结构。
3. 多步任务执行到中途才暴露跨领域需求，初始工具预筛无法覆盖。
4. 需要同时控制能力可发现性、上下文 token、注意力稀释和缓存稳定性。

### 语言信号 (用户的话里出现这些就应激活)

- “工具太多，模型总是选错” / “too many tools, poor tool routing”
- “怎么做 progressive disclosure / deferred tool loading？”
- “启动时要不要加载所有 Skills？” / “load all skills at startup?”
- “Agent 中途才发现缺工具怎么办？” / “runtime capability gap”

### 与相邻 Skill 的区分

- 与 `design-cache-stable-context` 的区别：本 skill 决定**加载什么、何时加载**；后者决定已加载内容放在哪里以复用缓存。
- 与 `choose-rag-retrieval-mode` 的区别：本 skill 检索能力定义；后者检索业务知识与证据。
- 与 `design-trusted-agent-tools` 的区别：本 skill 解决发现与上下文预算；后者解决 Skill/工具形态、权限和供应链信任。

## E — 可执行步骤 (Execution)

当 skill 被激活后，agent 应按以下步骤执行：

1. **盘点能力与路由冲突**
   - 为每项能力记录任务域、触发条件、禁用条件、风险、输入输出和详细内容体积；合并仅参数差异的同类工具。
   - 完成标准：能识别功能重叠、描述过宽和高风险能力，不以名称猜边界。
   - 判停条件：能力少且稳定、全量定义成本可忽略时，不引入分层基础设施。

2. **构造目录层**
   - 每项只保留稳定名称和路由式描述：何时用、何时不用、中英触发词、风险提示；目录按域分组并可版本化。
   - 完成标准：只读目录即可把代表任务路由到正确能力域，且常驻 token 符合预算。

3. **构造核心流程与细则层**
   - 核心层包含执行顺序、前置条件、例外、判停和验收；大 schema、脚本、模板与深层规范使用稳定引用放到细则层。
   - 完成标准：命中核心层后无需加载全部附件即可开始第一步，每个引用说明何时读取。

4. **加入运行时能力缺口循环**
   - 要求 Agent 描述当前缺少的动作或观察，不直接猜工具名；先匹配能力域，再匹配具体工具/Skill。
   - 完成标准：多步任务能在中间观察后再次发现能力，而非受限于开局集合。
   - 判停条件：候选均低于阈值时返回 `NOT_FOUND`，允许改写、用基础工具实现或转人工；不得强配。

5. **设计加载与状态协议**
   - 命中的完整内容只加载一次，记录版本和来源；schema 固定在首次出现位置，状态栏只维护轻量已加载列表。
   - 完成标准：重复请求不会重复注入同一内容，已加载能力可追溯且不会静默升级。

6. **做路由与成本对照**
   - 用直接命中、相邻诱饵、跨域多步和未找到任务比较全量加载与渐进加载的准确率、完成率、token、TTFT 和误触发。
   - 完成标准：渐进方案在规定预算内提高或保持完成率，所有高风险误路由均被拦截。
   - 判停条件：路由收益不能覆盖发现基础设施成本，或弱模型无法稳定理解动态定义时，退回分域固定工具集。

## B — 边界 (Boundary)

### 不要在以下情况使用此 skill

- 只有少量、无重叠、低 token 的稳定工具，全量暴露更简单可靠。
- 参数嵌套复杂、高风险或需强审计的能力；发现后仍应调用结构化专用工具，不能用自然语言 Skill 替代安全边界。
- 用户只是想减少长轨迹噪声，能力数量并不大；应使用隔离/压缩治理。

### 作者在书中警告的失败模式

- **ce016 Skill 描述过宽导致误路由**：功能介绍不能代替触发与禁用条件。
- **ce017 启动时加载全部 Skill 和工具**：无关内容同时浪费 token、稀释注意力并扩大选择空间。
- **ce038 工具粒度过细造成选择爆炸**：分层发现不能修复本身不合理的工具建模。
- **ce052 按初始查询一次性预筛工具**：后续观察会产生新需求，发现必须可在运行中再次发生。

### 作者的盲点 / 时代局限

- Agent Skills、MCP 和原生 tool search 仍快速演化，具体注入格式与性能数字不应当作长期标准。
- 主动工具发现需要索引、版本、权限和供应链运维，中小团队可能因复杂度得不偿失。
- 书中依赖较强模型理解自然语言路由与散落 schema；较弱或非工具训练模型可能更适合固定分域菜单。

### 容易混淆的邻近方法论

- 渐进披露不是向量 RAG 的同义词：它加载的是可执行方法与接口定义，而不是回答问题的领域证据。
- 按需加载不代表动态改写稳定前缀；缓存位置需要单独设计。
