# 稳定前缀-动态后缀上下文布局

## R — 原文 (Reading)

> 动态信息永远追加到末尾——时间戳、用户状态等变化的内容，作为新消息追加到对话末尾，而不是修改已有的系统提示词。
>
> — 李博杰，第 2 章 2.3「KV Cache 友好的上下文设计」，PDF 第 50 页（书内第 42 页）

---

## I — 方法论骨架 (Interpretation)

缓存复用比较的是 token 前缀是否一致，不是两段提示在语义上是否等价。上下文中越靠前的变化，重新计算范围越大。因此布局应先按**变化频率**而不是只按语义章节划分：

- 系统规则、稳定工具定义和静态文档构成字节级稳定的前缀。
- 时间、用户状态、新观察、临时 Skill 和新发现工具只追加到轨迹后部。
- 同一工具集合采用确定性顺序与序列化；已追加的 schema 留在首次出现的位置，不反复搬到末尾。
- 当前最重要的动态状态靠近上下文末端，兼顾注意力边缘效应。

缓存指标只是约束之一。布局优化必须同时保证模型行为、任务状态和结构化消息格式不退化；为追求命中率删除历史或打乱语义，会从性能优化变成功能故障。

## A1 — 书中的应用 (Past Application)

### 案例 1：错误上下文管理实验（c006）
- **问题**：模型和请求长度没变，客服 Agent 首 token 延迟和账单却突然上升，长任务还出现重复调用。
- **方法论的使用**：作者分别测试系统提示中的动态时间戳、动态用户配置、工具 schema 重排和滑动窗口。
- **结论**：前缀首个变化点决定后续缓存失效；语义相同的工具重排也会重算；机械裁剪会破坏任务状态。
- **结果**：动态前缀和工具重排使缓存命中下降；滑动窗口导致失忆和重复执行。

### 案例 2：120+ 工具的主动发现（c032）
- **问题**：小模型启动时加载 50K+ token 的全部工具 schema，工具选择退化且每次变更破坏缓存。
- **方法论的使用**：静态前缀只保留基础工具和发现入口；新 schema 在首次命中时追加到轨迹，并固定在原位置。
- **结论**：能力目录可以稳定常驻，详细工具定义按需进入动态轨迹，无需修改系统前缀。
- **结果**：实验方案以约 2K token 稳定前缀替代全量注入，并预期显著提高小模型任务完成率；书中未报告最终统一量化表。

## A2 — 触发场景 (Future Trigger)

### 用户会在什么情境下需要这个 skill?

1. 多轮请求内容相近，但 prompt cache/KV cache 命中率低或首 token 延迟波动大。
2. 系统提示每轮注入时间、用户状态、随机值或会话配置。
3. 工具集合相同但注册、排序或序列化不稳定，重启后性能变化。
4. 动态加载 Skill/工具时，不确定 schema 应插到系统前缀还是轨迹中。

### 语言信号 (用户的话里出现这些就应激活)

- “为什么 prompt cache 一直 miss？” / “low KV cache hit rate”
- “stable prefix / dynamic suffix 应该怎么设计？”
- “工具 schema 顺序会影响缓存吗？” / “does tool ordering break prompt caching?”
- “加了一行时间戳，TTFT 和成本突然上升” / “dynamic timestamp increased TTFT”

### 与相邻 Skill 的区分

- 与 `distill-explicit-agent-state` 的区别：本 skill 决定信息放置与缓存边界；后者决定哪些隐式运行状态应由代码计算并显式注入。
- 与 `isolate-before-compressing-context` 的区别：本 skill 解决前缀复用和布局；后者解决长任务噪声、容量与信息损失。
- 与 `progressively-disclose-capabilities` 的区别：本 skill 优化加载后的 token 位置；后者设计何时发现和加载哪种能力。

## E — 可执行步骤 (Execution)

当 skill 被激活后，agent 应按以下步骤执行：

1. **建立请求序列化基线**
   - 保存连续多轮的最终 API 消息、工具定义、token 数、前缀哈希、缓存命中、TTFT 与成本。
   - 完成标准：能定位相邻请求的首个 token/字段变化点，而不是只比较语义。
   - 判停条件：若服务端不提供缓存且任务是单次短调用，停止使用本 skill，以普通上下文清晰度优化为主。

2. **按变化频率分类内容**
   - 分成稳定规则、稳定工具、会话级状态、轮次级状态、新观察和按需能力；标注更新频率与必要位置。
   - 完成标准：每个上下文字段都有“谁更新、何时更新、是否允许原地修改”的归属。

3. **构造稳定前缀**
   - 固定系统提示、静态参考和核心工具；采用确定性排序、稳定 JSON 序列化和标准 API 消息，不在前部插入时间与请求状态。
   - 完成标准：相同版本的静态前缀跨请求字节一致，哈希稳定。

4. **设计只增不改的动态轨迹**
   - 将时间、状态、新观察和命中的 schema 追加到后部；schema 首次出现后留在原位置，不在每轮搬运、删除或重排。
   - 完成标准：新一轮只增加新消息，历史块在压缩阈值前不被原地改写。

5. **同时验证性能与行为**
   - 在固定任务集比较命中率、TTFT、输入成本、成功率、工具误选和重复调用；单独测试缓存 TTL 过期。
   - 完成标准：性能指标达到预设改善，行为保留集不退化，状态未因布局改变丢失。
   - 判停条件：命中提升但成功率或状态保真下降时回滚；不要用缓存收益抵消功能错误。

6. **建立变更纪律**
   - 系统提示、工具 schema 和顺序改变时显式升版本；监控前缀哈希，避免无意空格、随机顺序和静默升级。
   - 完成标准：每次缓存失效都能解释为版本、TTL 或明确动态边界，而非未知漂移。

## B — 边界 (Boundary)

### 不要在以下情况使用此 skill

- 单次、短上下文调用，缓存收益低于维护稳定序列化的复杂度。
- 问题是长轨迹噪声或关键状态丢失，而不是前缀失效；使用压缩/隔离或状态栏方法。
- 为保持前缀不变而阻止必要安全规则、权限或事实更新；正确性优先于缓存命中。

### 作者在书中警告的失败模式

- **ce008 把动态信息写进稳定前缀**：一行时间戳会使该位置之后的 KV 状态无法复用。
- **ce009 动态重排工具定义破坏缓存**：缓存按 token 匹配，不理解 schema 集合“语义等价”。
- **ce020 追加式状态造成新旧版本歧义**：只增不改若没有版本、有效期和取最新规则，会让模型同时看到冲突状态。

### 作者的盲点 / 时代局限

- Prompt Cache、可编辑 KV Cache 和厂商 API 快速变化，书中的具体实现与命中率数字可能很快过时；应保留“首个变化点”原则并以当前运行时实测。
- 本书偏高调用量 Agent；低流量系统可能不值得用额外架构复杂度换缓存收益。
- 缓存成本不是唯一目标，隐私隔离、租户边界和合规要求可能禁止跨请求复用某些前缀。

### 容易混淆的邻近方法论

- “动态内容追加”不等于永不整理；达到治理阈值后仍需版本化压缩或新会话边界。
- “稳定前缀”不等于把所有工具常驻；详细能力仍可通过渐进披露按需加载。
