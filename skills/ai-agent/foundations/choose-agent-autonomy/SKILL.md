# 按动态性与可验证性分配自治

## R — 原文 (Reading)

> 对于可以清晰分解为固定子任务的场景，考虑使用工作流；只有当需要动态决策和灵活的执行路径时，才使用自主 Agent。
>
> — 李博杰，第 1 章 1.2.5「编排模式：工作流与自主」，PDF 第 30 页（书内第 22 页）

---

## I — 方法论骨架 (Interpretation)

自治不是产品标签，而是一种按任务局部授予的控制权。选择时先看两条轴：

- **路径动态性**：正确步骤能否在运行前枚举，还是必须根据新观察临时决定下一步。
- **验证自动化**：系统能否用测试、数据库状态或确定规则判断完成，还是只能靠人工与主观判断。

固定且可验证的任务优先确定性工作流；动态且可验证的任务才适合更高自治。目标模糊或结果难验时，增加自治只会加速跑偏，应先澄清目标、缩小动作空间或保留人工门。单次调用、工作流和自主 Agent 可以在同一产品内组合：常规主干固定，真正不可枚举的异常分支局部自治，高风险提交点重新收回控制权。

## A1 — 书中的应用 (Past Application)

### 案例 1：司法问答中的 Agentic RAG 对照（c021）
- **问题**：是否所有检索问答都应由 Agent 自主分解、评估并多次检索。
- **方法论的使用**：作者把单一信息需求与复杂量刑多跳问题分开，比较传统单次 RAG 和 Agentic RAG。
- **结论**：简单问题的路径固定且一次检索已足够；多跳问题的证据路径依赖中间结果，才值得自治。
- **结果**：简单任务中传统 RAG 更快且质量相近；复杂任务中 Agentic RAG 以额外延迟换取更高鲁棒性和准确率。

### 案例 2：AndroidWorld 分阶段改进（c055）
- **问题**：移动端任务失败后，是否应把所有有效机制全量加入 Agent。
- **方法论的使用**：作者先按任务簇定位导航、转录和计数问题，每轮只增加针对性机制并记录成本。
- **结论**：有效改动也有 token 和延迟代价，自治与 Harness 复杂度必须按局部收益部署。
- **结果**：对应成功率显著提高，但成本证据阻止团队把所有机制无差别全量开启。

## A2 — 触发场景 (Future Trigger)

### 用户会在什么情境下需要这个 skill?

1. 新建 LLM 应用，不确定单次调用、固定工作流还是自主 Agent 哪种编排更合适。
2. 现有自动化在少数异常上卡住，团队考虑把整个流程改成 Agent。
3. 高风险业务希望提高自动化率，但需要决定哪些决策、动作或提交点必须保留人工。
4. Agent 成本、延迟和故障点增长，需判断哪些自治没有带来性能增益。

### 语言信号 (用户的话里出现这些就应激活)

- “这个需求要不要做成 Agent？” / “do we need an autonomous agent?”
- “工作流和 Agent 怎么选？” / “workflow vs agent”
- “哪些步骤可以自动，哪些必须人工确认？” / “human-in-the-loop boundary”
- “固定流程里只有异常分支不确定，怎么设计？” / “local autonomy for exceptions”

### 与相邻 Skill 的区分

- 与 `diagnose-agent-boundaries` 的区别：本 skill 在架构层分配自治；后者对一个具体失败做观察-策略-动作-反馈归因。
- 与 `choose-rag-retrieval-mode` 的区别：本 skill 适用于所有 Agent 编排；后者只处理检索问题的单跳、多跳和全库聚合几何。
- 与 `design-trusted-agent-tools` 的区别：本 skill 决定控制路径；后者决定高风险能力应以何种接口和信任边界表达。
- 与 `formalize-and-verify-agent-work` 的区别：先由后者识别可确定执行和外部验收的部分；本 Skill 再只为剩余动态决策分配自治，而不把形式化本身当 Agent 化。

## E — 可执行步骤 (Execution)

当 skill 被激活后，agent 应按以下步骤执行：

1. **写出任务与副作用边界**
   - 列出输入、最终环境状态、必须遵循的顺序、不可逆动作、人工责任和成本/延迟预算。
   - 完成标准：每个任务都有可观察目标，所有副作用已标风险等级。
   - 判停条件：若“优化体验”“帮我处理好”等目标没有验收标准，先澄清，不进入架构选型。

2. **评估路径动态性**
   - 对每个节点判断：步骤和分支能否预先枚举；下一步是否依赖运行时新观察；异常是否可用有限状态机覆盖。
   - 完成标准：得到固定节点、动态决策点和未知异常三类清单，并给出实际样本佐证。

3. **评估验证自动化**
   - 为每个节点指定环境真值、确定性验证器、人工 Rubric 或“目前不可验证”；不要把模型自报算验证。
   - 完成标准：每个候选自治动作都有成功、失败和超时判据。
   - 判停条件：动态节点不可自动验证且副作用高时，不授予自治，转人工或先缩小任务。

4. **选择最小可行编排**
   - 单步且提示可解：单次调用。
   - 多步但路径固定：确定性工作流，LLM 只在节点内理解/生成。
   - 路径依赖新观察且可验：在该局部使用自主循环。
   - 目标模糊或难验：先澄清、沙盒试验或人工主导。
   - 完成标准：架构图中每个自主节点都由一个不可预枚举的决策需求证明。

5. **收紧自治护栏**
   - 给自主段设置动作白名单、轮数/时间/费用上限、提交前确认和人工升级；常规主干仍走确定性路径。
   - 完成标准：每个自主循环有成功、预算耗尽、不可恢复错误三类出口。

6. **用等预算对照决定是否升级**
   - 在真实任务上比较更简单方案与候选方案的成功率、连续可靠性、延迟、成本和安全 veto。
   - 完成标准：新增自治带来预先设定的净收益，且保留集无不可接受退化。
   - 判停条件：成功率无显著提升，或收益小于成本/风险时，退回更简单模式；不要用“看起来更智能”作为升级理由。

## B — 边界 (Boundary)

### 不要在以下情况使用此 skill

- 已经有固定堆栈与可复现 bad case，用户只想找具体故障；使用 `diagnose-agent-boundaries`。
- 用户只是问如何写单条提示词，且不存在多步工具路径或环境副作用。
- 法规、付款、删除或部署等固定高风险流程不能因“灵活”绕过确定顺序与审批。

### 作者在书中警告的失败模式

- **ce001 把固定任务过度 Agent 化**：没有新增信息或不可枚举决策，只增加 token、延迟和故障点。
- **ce054 在目标模糊时执行优化**：没有验收函数时，自治系统只会高效优化自己选择的代理目标。
- **ce055 模型自报完成替代环境验收**：自主循环必须由环境状态而非完成措辞停止。

### 作者的盲点 / 时代局限

- 本书来自高风险、长流程 Agent 实践，可能高估复杂 Harness 对低风险短流程的价值；传统软件常是更好默认值。
- 任务动态性和验证难度在运行前不一定可准确估计，应允许小流量证据修正初始分类。
- 当前模型和工具调用范式快速变化，自治成本阈值会变；应保留判断轴，不固化书中的产品与性能数字。

### 容易混淆的邻近方法论

- “路径动态”不等于“业务规则很多”；规则很多但可枚举，仍适合工作流。
- “模型很强”不等于“可以高自治”；没有独立验证的高风险动作仍应受限。
