# 在线执行-离线进化与可信根

## R — 原文 (Reading)

> 在线执行循环只完成任务并记录证据，不直接改写正式 Agent；离线进化循环聚合轨迹、诊断根因、生成更新提案，再通过验证门槛发布新版本。

来源：第 8 章 8.3 “构建可长期运行的持续进化闭环”，PDF 第 249 页。

## I — 内化 (Internalization)

保存轨迹、检索记忆和改变未来正式行为是三件不同的事。持续进化必须形成可追踪的因果链：运行证据经过评价、归因、归纳、候选更新、独立验证和受控发布，才称为学习。

在线执行循环面对不可信用户输入、瞬时故障和不可复现反馈，只应完成任务、记录版本化轨迹与外部结果。它不得直接拥有覆盖正式 Prompt、Skill、程序、参数或安全规则的权限。

离线进化循环按任务族聚合成功、部分成功和失败轨迹，以外部结果先评价，再诊断根因，选择更新载体，生成带来源的最小候选 diff。候选不是正式能力。

发布门由回归、迁移、安全、权限、成本与延迟验证组成。通过后先 canary，再逐步放量；异常触发自动回滚。新经验既要能被记住和迁移，也要在冲突时正确更新，并保留仍有效的旧能力。

最关键的是可信根：基线版本、隐藏测试、发布审批、权限边界、预算、审计日志和回滚指针必须位于被进化 Agent 的修改权限之外，否则系统可以通过改标准证明自己“进步”。

## A1 — 作者案例 (Author's Cases)

### 案例 1：Hermes 外部审核的自我改进流程

- **问题**：Agent 怎样提出自身改进，又不让提议者拥有自证和直接发布权？
- **方法**：实验 8-8 将稳定版本、测试、审批与修改权限分离；Agent 只生成候选，外部流程审核后决定是否接纳。
- **结论**：自我改进需要不可由候选版本改写的可信根。
- **结果边界**：候选被接纳只证明发布流程工作，不证明长期连续进化带来总体净收益。

### 案例 2：连续进化的四项联合测试

- **问题**：新经验加入后，怎样区分真正进化与记忆堆积或负迁移？
- **方法**：实验 8-9 同时检查记住新经验、迁移到新任务、冲突时更新旧规则、保留仍有效旧能力。
- **结论**：四项必须联合成立；只在新样本上变好不足以发布。
- **结果边界**：该实验是机制验证，不能替代长期生产事故率、维护成本和跨模型复现。

## A2 — 适用场景 (Application)

### 何时调用

1. 计划从生产轨迹、用户反馈、测试结果或人工修正持续更新 Agent。
2. Agent 被允许修改自己的 Prompt、Skill、知识、程序或参数，需要治理权限与发布边界。
3. 经验库持续增长但相同失败重复发生，怀疑“保存”并未转化为可靠学习。
4. 需要设计候选版本、离线验证、canary、自动回滚、审计和可信根。
5. 收到 “continuous agent evolution”, “safe self-improvement”, “online learning governance”, “self-modifying agent with rollback”等英文请求。

## E — 执行步骤 (Execution)

### 1. 画出权限与可信根

列出正式 Agent 可读写资源，以及不可修改的基线、隐藏测试、审批规则、预算、审计日志、版本仓库和回滚指针。默认拒绝在线写正式能力。

- **完成标准**：权限矩阵能证明执行 Agent 无法直接修改任一可信根，所有持久写入都有身份、来源和审计事件。
- **判停点**：若生产 Agent 能改测试、审批或当前正式版本，先收回权限，不继续自动进化设计。

### 2. 分离在线执行循环

在线仅记录输入、动作、工具结果、最终环境状态、版本、成本、用户反馈与安全事件；敏感内容做最小化和访问控制。

- **完成标准**：每条轨迹可重放或至少可验证关键状态，并能追到唯一 Agent/工具/知识版本；在线没有正式发布能力。
- **判停点**：轨迹缺少工具结果、结果真值或版本，不能进入学习池，只用于故障调查。

### 3. 建立离线证据门槛

先用外部结果评价，再按任务族聚合成功、部分成功和失败，寻找跨案例稳定机制；记录适用条件、例外、反证和置信度。

- **完成标准**：每个更新提案至少有支持证据、反例检查和根因解释；低置信或单轨迹偶然关联被隔离。
- **判停点**：没有先评价就只有模型反思，或证据只能来自一次成功时，不生成正式候选。

### 4. 生成最小、可逆候选

调用载体路由，生成带来源的知识条目、指令 diff、程序补丁或参数候选；禁止全量重写。候选使用独立版本号和变更范围。

- **完成标准**：diff 可人工审查、可一键撤销，且每个变更行都能回指触发证据和预期测试。
- **判停点**：更新影响范围无法界定、旧规则被无来源删除，或候选能改自己的验证门时拒绝。

### 5. 运行联合发布门

验证目标 canary、相邻任务、OOD、旧任务回归、安全权限、成本与延迟；专门测试记忆、迁移、冲突更新、旧能力保留四项。

- **完成标准**：全部硬门通过，主指标达到最小改善阈值，安全零容忍项无违规，验证报告由候选权限之外的系统签名。
- **判停点**：任何安全门或旧能力保留失败立即拒绝，不能用目标 canary 的高收益抵消。

### 6. Canary 发布与自动回滚

从影子/小流量开始，限定人群、任务、时间和预算；实时比较基线，监控失败类型而非只看平均分。逐级放量需独立批准。

- **完成标准**：canary 达到预定样本量和观察期，各项指标在置信边界内优于或不劣于基线；回滚演练通过。
- **判停点**：安全事件、重复新失败、关键指标越界或证据链断裂时自动回滚并冻结继续放量。

### 7. 归档与防代际漂移

保留原始证据、候选、验证、审批、发布与回滚记录；定期从原始真源重建索引和摘要，淘汰过期经验但不删除审计链。

- **完成标准**：任一线上行为可追到生效版本和批准证据；派生摘要可从原始材料重建；旧版本可恢复。
- **判停点**：知识只能追到另一份摘要，或历史版本/测试不可恢复时，暂停下一轮进化。

## B — 边界与禁区 (Boundary)

### 不要在以下情况使用

- 单次任务内的普通上下文记忆：无需建立版本进化流水线。
- 只有日志存储或相似案例检索，却不改变正式行为：这是可观测性/记忆，不应宣称持续学习。
- 没有独立评测、权限隔离和回滚能力：只收集证据，不自动发布。
- 任务短、低风险且规则完全确定：普通程序和人工版本管理往往更便宜。

### 明确反例与警告

- **ce081 保存不等于学习**：轨迹写入向量库不会自动得到可迁移规则。
- **ce082 在线自改**：未经验证反馈立即覆盖正式能力，会把噪声、提示注入和偶发故障长期固化。
- **ce083 先反思后评价**：模型不知道真实成败却总结教训，会持久化错误因果。
- **ce085 单例过拟合**：一次成功无法区分必要策略与偶然共现。
- **ce086 全量重写**：整份 Prompt/记忆代际重述会丢规则、扩大改动面并破坏回滚。
- **ce087 无回归发布**、**ce089 自改验证器**、**ce090 指令代替硬门**、**ce091 无 canary/rollback** 都破坏可信发布链。

### 阶段 0 批判边界

- 全书缺少多年生产纵向数据，实验 8-8/8-9 主要证明机制可行，不能证明持续进化的长期收益高于维护与治理成本。
- 书中使用 2025-2026 年模型、Skill、Harness 和后训练假设；原生长期记忆或可验证自修改模型可能重画在线/离线边界，但可信根原则仍需实测保留。
- 作者长期工作流与高风险系统背景会高估自治和复杂 Harness 的必要性；很多短流程应由人工审核或普通 CI/CD 管理。
- 独立验证、canary 和回滚需要数据、基础设施与组织责任，小团队资源不足时应限制自动化范围，而不是降低发布门槛。
