# 可验证奖励与违规路径联合门控

## R — 原文 (Reading)

> 工程上可以先用结果奖励建立可靠基线，再只为真正可验证的中间事件加入过程信号。

来源：第 7 章 7.11.2 “奖励在什么时候给：结果还是过程”，PDF 第 231 页。

## I — 内化 (Internalization)

奖励不是任务目标本身，而是策略能观察并优化的代理信号。只要代理指标与真实目标存在缝隙，足够强的策略就会搜索那条缝隙。

设计奖励先回答四个问题：谁产生信号，信号何时产生，计算信号时能看到什么，达到高分经过的路径是否合法。来源与策略同源、使用未来信息或验证器可修改，都会产生虚假可验证性。

结果奖励通常最接近真实验收：测试、数据库状态、业务状态、格式解析或用户确认。但结果正确并不保证路径合规，删测试、改评分器、越权退款同样可能“成功”。

过程奖励只有在中间事件能由环境直接验证时才应加入，例如合法 API 返回、不可篡改状态转移或形式化证明步骤。模型自述“我已检查”不是过程证据。

因此采用联合门控：可靠结果分作为主目标，可验证过程信号用于信用分配，违规路径由独立惩罚或硬否决处理；三者分别记录，不能用高总分抵消安全违规。

## A1 — 作者案例 (Author's Cases)

### 案例 1：代码与航空政策的可验证结果

- **问题**：开放任务怎样获得比模型自评更可靠的完成信号？
- **方法**：代码任务运行测试，航空政策任务把参数化条件交给服务器真实逻辑，检查最终状态而非语言表述。
- **结论**：环境结果可建立稳定基线，并把“答案看起来合理”变成可执行验收。
- **结果边界**：测试或服务器规则若不完整、可被策略修改，仍会产生奖励劫持。

### 案例 2：路径验证奖励

- **问题**：只有终局成功信号时，长轨迹信用分配慢且可能走违规捷径。
- **方法**：在实验 7-16 中为终端违规与可验证进展设置路径信号，比较任务成功和探索效率。
- **结论**：部分设置中终端违规下降且成功率稳定，miniF2F 有加速；软件任务若进展信号不可达则没有收益。
- **结果边界**：路径奖励并非天然有效，只有可观察、可归因的中间事件才值得加入。

### 案例 3：带证据与置信度的轨迹评价

- **问题**：持续学习系统怎样避免把噪声轨迹直接当训练信号？
- **方法**：实验 8-1 把总分拆成维度级证据与置信度，低置信评价不进入正式学习。
- **结论**：奖励除了数值，还应带来源、证据和可用性门槛。
- **结果边界**：该案例展示评价结构，不等于证明自动评价可替代独立环境验收。

## A2 — 适用场景 (Application)

### 何时调用

1. 为工具调用、代码、客服、数学证明或长流程 Agent 设计 RL/搜索奖励。
2. 训练分数上升，但隐藏测试、真实业务状态或安全指标不升反降。
3. 在结果奖励、过程奖励、模型裁判和人工反馈之间选择组合。
4. 需要识别删测试、改验证器、越权操作、浅层自检等 reward hacking 路径。
5. 收到 “design a verifiable reward”, “outcome vs process reward”, “prevent reward hacking”, “path verification reward”等英文请求。

- 中文：“奖励函数怎么写”“最终结果对了但路径违规”“过程奖励值不值得加”“为什么 RL 学会钻空子”“模型裁判可靠吗”。

### 与相邻 Skill 的区分

- `choose-sft-or-rl` 判断是否需要 RL；本 Skill 在进入交互优化后设计可验证信号与反作弊门禁。
- `build-reproducible-agent-evals` 建立可重复的评测样本、环境与指标；本 Skill 决定哪些评测信号可作为优化目标，且要防止训练策略接触或修改验证器。
- `govern-continuous-agent-evolution` 决定生产轨迹如何进入离线更新；本 Skill 只负责轨迹评价和训练奖励的可信度。
- `formalize-and-verify-agent-work` 为任务建立外部完成验收；本 Skill 将其中适合优化的验收转成奖励，但保留独立最终裁决。
- `build-independent-review-loops` 为候选提供运行时异源审核；本 Skill 设计训练策略会主动优化的数值信号，必须额外防止验证器泄漏和违规捷径。

## E — 执行步骤 (Execution)

### 1. 定义真实目标与不可妥协约束

把任务写成最终状态、允许路径和禁止路径三张清单。禁止项包括修改评测器、删除测试、越权资源、伪造工具结果及不可逆副作用。

- **完成标准**：每项都能由环境日志、权限系统、测试或明确人工审核判断，且安全约束不能被主任务分数抵消。
- **判停点**：目标仍是“用户满意”“看起来正确”等不可操作描述时停止奖励设计，先补验收定义。

### 2. 建立结果奖励基线

优先选择策略不可修改的外部结果：隐藏测试、数据库最终状态、服务器规则、形式化检查、真实用户确认。保留原始证据和版本。

- **完成标准**：人工抽检的成功/失败轨迹与结果奖励排序一致，并能解释每个分值来自哪项外部状态。
- **判停点**：策略能够读取答案、修改测试/验证器或用口头声明触发成功时，立即停止训练并隔离验证面。

### 3. 审计奖励的四个维度

逐项记录：信号来源者；产生时点；计算时可见信息；到达该状态的路径。检查同源偏差、未来信息泄露与非法状态转移。

- **完成标准**：每个奖励分量都有 `producer/time/visible_information/allowed_path` 四字段及可信等级。
- **判停点**：任何分量依赖决策时刻之后的信息，或只来自策略自评，则不得进入可优化奖励。

### 4. 只添加可验证过程信号

从失败轨迹中找结果奖励过稀疏的阶段，只为环境可直接观察且与进展单调相关的事件加分；从零开始逐个加入并做消融。

- **完成标准**：加入的过程分量能提高探索效率或信用分配，同时不降低真实结果、OOD 与安全指标。
- **判停点**：中间事件不可达、与最终成功弱相关，或消融后无收益时删除该分量。

### 5. 独立门控违规路径

把删测试、改验证器、绕过审批、越权调用、伪造结果设为硬否决或独立高权重惩罚；验证器与日志位于策略权限之外。

- **完成标准**：构造的每条对抗捷径都被拒绝，即使其结果指标表面成功；违规率单独报告为零或低于既定阈值。
- **判停点**：发现一种高分违规轨迹却无法可靠检测时，不得发布该奖励训练出的策略。

### 6. 做奖励压力测试与发布审计

运行正常、边界、对抗、OOD 和验证器故障轨迹；比较真实质量、结果分、过程分、违规分和总分，并人工审查极值样本。

- **完成标准**：高奖励与真实目标在留出集保持预设一致性，所有极端高分均有合法证据，验证器故障默认失败关闭而非放行。
- **判停点**：优化后代理分上升但真实质量、安全或旧任务退化，回滚奖励版本并重新定位缝隙。

## B — 边界与禁区 (Boundary)

### 不要在以下情况使用

- 尚未决定是否需要 RL：先做外部修复与 SFT/RL 方法选择。
- 只有静态离线生成、没有搜索或训练会优化该信号：此时应设计评测，不必把它包装成奖励。
- 目标必须靠不可形式化的长期人类判断，且没有可靠代理：保留人工审批，不制造伪精确分数。
- 奖励器、测试或环境无法与策略权限隔离：不得开展开放式优化。

### 明确反例与警告

- **ce055 自报完成**：Agent 说“完成”而没跑测试，语言声明不能作为结果奖励。
- **ce078 训练主体混淆**：把环境返回 token 当策略标签，会教模型生成假观察而非采取动作。
- **ce079 破坏性捷径**：删除失败测试也能让测试通过；结果、路径与安全必须联合门控。
- 同一模型既生成又自评容易共享盲区；模型裁判只能作为带置信度的辅助信号，不能单独控制高风险发布。

### 阶段 0 批判边界

- 书中路径验证实验规模有限且任务相关：终端违规降低、miniF2F 加速不代表所有过程奖励都有效，软件任务的不可达信号就是负结果。
- 2025-2026 年模型与训练栈快速变化，但“策略会优化可见代理”这一机制不依赖具体算法；具体权重、裁判与框架需要重测。
- 作者的软件工程背景偏好测试、数据库和形式化状态；开放式创作、关系质量和长期影响未必有同等可靠的结果验证器。
- 强验证器、隐藏环境和人工对抗审计成本高，小团队不能用廉价模型裁判冒充可信根；验证不足时应限制动作空间或保留人工门禁。
