# 将 Agent 工作形式化并执行验证

## R — 原文 (Reading)

> 新的协同模式是：让 LLM 负责理解用户的自然语言问题，识别其中的数学或逻辑结构，并转化为形式化语言（如 Mathematica 语言或 Python 的 SymPy 库） ；然后交给专门的符号计算引擎或约束求解器执行，获得精确结果。
>
> — 李博杰，第 5 章 5.2.1「代码作为思考工具」，PDF 第 154 页

---

## I — 方法论骨架 (Interpretation)

LLM 擅长理解含糊语言、识别实体关系和把问题映射到结构；它不应同时充当精确计算与最终真值。
先把任务中的主体、变量、单位、时段、条件、优先级、例外和目标转成可检查的中间表示。
存在关键歧义时，模型应列出解释并请求澄清，不能通过随机采样替业务制定政策。
确定的数学、逻辑、统计、权限和流程规则应编译为代码、约束、查询或参数化工作流。
执行器负责求值，数据库、测试、状态差异和不变量负责验收；模型只解释证据，不复制大规模数据。
服务端真值与用户输入、模型自报值要分开，模型不能用自己填写的字段证明自己正确。
若执行失败，反馈应回到“语义映射或形式化表达”层修正，而不是让模型口头覆盖执行结果。
稳定重复流程可以从一次探索轨迹中参数化，但必须加入动作前、动作后和最终状态检查。
形式化的目标不是用代码替代所有判断，而是把可确定部分从概率生成中剥离，让剩余歧义显式可审。

## A1 — 书中的应用 (Past Application)

### 案例 1：代码辅助数学与逻辑求解
- **问题**: 纯思维链在精确计算和多约束组合上容易漏条件或口算错误。
- **方法论的使用**: 实验 5-1/5-2 让 Agent 把数学题转成 SymPy/NumPy/SciPy 计算，把骑士与无赖谜题转成约束求解，再读取执行结果。
- **结论**: 模型负责表示转换，执行器负责确定求值；反馈可纠正语言推导中的错误。
- **结果**: K&K Puzzle 的代码辅助模式准确率超过 90%，显著高于纯思考模式，弱模型获益更明显。

### 案例 2：代码化航空政策约束
- **问题**: 小模型面对退款、改签等组合政策时，纯自然语言规则容易遗漏前置条件或相信自己编造的订单状态。
- **方法论的使用**: 实验 5-3 组合自然语言解释、参数 checklist 和服务端数据库真值校验；模型显式填条件，但最终裁决基于真实订单。
- **结论**: 自然语言适合解释例外，结构化参数强制核对，服务端代码作最后守门员。
- **结果**: 实验以违规、无效调用及模型自报值与数据库真值差异作为拦截验收，证明真值校验不可省略。

### 案例 3：PreAct 可验证工作流
- **问题**: 浏览器 Agent 每次都重新探索相同流程，慢且容易在页面变化后盲目回放旧动作。
- **方法论的使用**: 作者将成功轨迹抽象并参数化为程序，为每步加入执行前/后检查，在独立重置环境完整回放后才发布。
- **结论**: 一次探索可编译成程序，但可复用性来自状态验证和失效回退，而不是动作录制本身。
- **结果**: 重复任务端到端加速 8.5-13 倍；检查失败时回退到完整 Agent。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. Agent 要做数学、财务、税务、资格、配额、时间或跨条款逻辑计算，结果必须精确可复核。
2. 自然语言政策有条件、例外、优先级和冲突，重复运行得到不一致决策。
3. 要对全库数据统计、聚合或生成 SQL，不能让模型搬运和心算大量结构化数据。
4. 一段 GUI/API 探索流程反复出现，希望固化为更快的参数化工作流。
5. 模型输出流畅但无法提供执行结果、数据库状态、测试或不变量作为证明。

### 语言信号 (用户的话里出现这些就应激活)

- “不要让模型口算，能不能写代码验证？” / “use code to verify”
- “把这些规则转成约束/状态机。” / “formalize as constraints”
- “同一政策模型每次解释不一样。” / “deterministic policy enforcement”
- “让 LLM 只生成 SQL，数据不要经过模型。” / “LLM should not copy the data”
- “把成功操作固化成可回放工作流。” / “compile trajectory into a verified workflow”

### 与相邻 Skill 的区分

- 与 `design-trusted-agent-tools` 的区别: 本 skill 关注语义到形式表示、执行与真值验证；工具设计 skill 关注接口粒度、权限、沙箱和供应链。
- 与 `build-reproducible-agent-evals` 的区别: 本 skill 验证单个任务或工作流的确定部分；后者构造跨任务、可重置、带统计与 Judge 校准的评估系统。
- 与 `attribute-first-errors` 的区别: 本 skill 是解题架构；首错归因 skill 是失败发生后定位哪一步表示或执行最先偏离。
- 与 `build-independent-review-loops` 的区别: 本 Skill 适合可编码、可求解或可确定验收的判断；后者处理无法完全形式化但能取得异源证据的开放式审核。

## E — 可执行步骤 (Execution)

当 skill 被激活后，agent 应按以下步骤执行：

1. **定义语义契约**
   - 提取主体、输入、单位、时段、变量、规则优先级、例外、目标、允许副作用和成功状态。
   - 完成标准: 每个业务名词有操作性定义；单位和时间边界明确；未知项与假设单独列出。
   - 判停条件: 若关键裁量无法从政策或用户确认中确定，停止执行并请求澄清，不得自行发明阈值。

2. **选择最小形式表示**
   - 计算用代码/表达式，组合约束用规则表或求解器，数据聚合用 SQL/数据框，重复流程用参数化状态机或工作流。
   - 完成标准: 形式表示能覆盖全部已知条件和例外，且比自然语言原文更容易执行与审查；不引入无关框架。

3. **生成可审查的中间表示**
   - 保留每条自然语言依据到变量、约束或代码行的映射；对多种解释输出备选，而非静默选一条。
   - 完成标准: 审查者能从任一关键计算回溯到来源规则；所有默认值显式可见。

4. **在确定性执行器中求值**
   - 使用受限代码环境、查询引擎、规则引擎或工作流执行器；大规模数据从可信源直接进入执行与渲染层。
   - 完成标准: 运行可复现，输入与版本被记录；模型不负责抄写中间大数据，执行失败不会被口头答案覆盖。

5. **用独立真值和不变量验收**
   - 校验数据库状态、测试、守恒关系、类型/范围、边界样本、动作前后状态和最终业务结果。
   - 完成标准: 每个核心结论至少有一个非模型自报证据；高风险动作还经过稳定权限边界。

6. **按反馈修正表示而非改写真值**
   - 将失败归因到语义抽取、规则映射、实现或环境；最小修改后重新执行，并保留旧版本和差异。
   - 完成标准: 修复解释了失败证据，原用例和边界/反例全部重跑通过。
   - 判停条件: 连续两轮修改未改变失败证据，停止自动修正，输出未决歧义和人工复核点。

7. **交付结果与证明包**
   - 输出结论、形式化表示、输入版本、执行日志摘要、验证结果、未覆盖假设和适用边界。
   - 完成标准: 另一执行者可在不依赖本轮隐藏思考的情况下复现结果。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 目标是审美、价值权衡、谈判或其他无法定义客观约束和真值的开放判断；形式化只能辅助，不能冒充答案。
- 问题极简单、无组合条件且可直接由可信数据源回答，写代码会增加不必要故障面。
- 政策本身尚未确定或相互冲突；先由责任人澄清规则，不能让模型用代码把歧义冻结成“事实”。

### 作者在书中警告的失败模式

- 把业务规则堆成无序清单，模型临时推断控制流，组合任务成功率显著下降（ce012）。
- 用“合理、适当、必要时”等模糊裁量而不定义阈值、例外和升级路径（ce013）。
- 让 LLM 搬运大规模结构化数据，概率生成替代精确数据路径，产生抄数错误与高 token 成本（ce061）。
- 直接执行模型生成的 HTML、SQL 或脚本，或把权限判断写在同一份动态代码里（ce060、ce062）。
- 用模型自报完成替代测试和环境验收，形式化输出只是另一段未经执行的文本（ce055）。

### 作者的盲点 / 时代局限

- “代码是元能力”的证据主要来自数字任务；社会互动、隐性知识、物理操作和价值判断的可形式化程度有限。
- 全书偏 Python、Coding Agent 和文件系统范式，其他组织和合规环境可能需要不同执行基础设施。
- 更强模型可能减少部分脚手架收益；形式化成本必须与错误代价、任务频率和传统软件实现比较。
- 示例多依赖头部模型、沙盒和自动验证，中小团队应先从最小可复现执行器和少量关键不变量开始。

### 容易混淆的邻近方法论

- “让 Agent 写代码”不等于完成形式化；必须有语义映射、执行和外部验收三个阶段。
- 代码运行成功不等于业务正确，数据库真值、权限和边界条件仍需独立验证。
- 结构化输出只是中间表示；如果规则来源不明或含糊，JSON 再整齐也不会产生可靠结论。
