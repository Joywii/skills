# 设计可信 Agent 工具与执行边界

## R — 原文 (Reading)

> 支付、删除数据、发送邮件和生产部署等高风险或强业务约束操作，仍应封装为参数明确、权限受限且全程可审计的专用工具，必要时再加上预览和人工确认。
>
> — 李博杰，第 1 章 1.1.2「工具：Agent 的手脚」，PDF 第 19 页

---

## I — 方法论骨架 (Interpretation)

Agent 的能力有两层：Skill 说明“如何做”，工具与执行器决定“实际能做什么”。
先按副作用、权限和可逆性划定最窄动作空间，再选择能力的表达形式。
高频变化、以解释和流程为主的知识适合 Skill；稳定、低层、可确定执行的动作适合工具。
结构复杂、权限敏感、不可逆的动作应进入参数明确的专用工具，而不是开放 Shell 或浏览器。
通用代码执行器能覆盖大量低风险计算，但必须置于真正的系统沙盒中；venv 不是沙盒。
提示词、Skill、检索内容和第三方 MCP 元数据都可能被污染，因此不能承担最终授权。
权限过滤、参数校验、租户隔离和业务真值检查必须位于模型无法绕过的服务端或数据层。
模型看到的参数、工具实际执行的参数及返回结果必须一致；任何规范化都要显式披露。
接入第三方能力等于同时引入指令文本、代码行为和凭证风险，必须锁版本、审来源并最小化凭证。
目标不是把一切做成专用工具，而是在灵活性、上下文成本和不可绕过的安全边界之间作可审计取舍。

## A1 — 书中的应用 (Past Application)

### 案例 1：执行工具 MCP 服务器
- **问题**: 文件、终端、解释器、数据与 GUI 动作的风险和验证方式不同，统一开放会放大副作用。
- **方法论的使用**: 实验 4-3 为每类动作分别配置专用接口、超时、审查、沙箱和执行后验证；危险命令不只靠提示词阻止。
- **结论**: 工具协议可以统一，但权限、隔离和验证必须随动作风险分层。
- **结果**: 验收要求危险命令被审查、文件修改自动运行 lint、长输出显式截断并保存全文。

### 案例 2：权限内嵌数据对象
- **问题**: Agent 动态生成应用代码时，可能遗漏权限检查、越过状态机或跨租户读取数据。
- **方法论的使用**: 实验 5-12 把权限、校验、租户隔离和引用完整性下沉到稳定数据层，让生成代码只能使用受限身份和受信接口。
- **结论**: 约束者不能与被约束的动态代码处于同一信任域。
- **结果**: 合法招聘流程成功；越界工资、跳过状态机和跨租户读取均被数据层拒绝。

### 案例 3：提示注入的组合防御
- **问题**: 网页、Skill 或跨会话记忆中的恶意文本可能被模型误当成系统指令。
- **方法论的使用**: 实验 2-5 区分直接注入、间接注入和记忆注入，并组合来源标记、指令/数据隔离与执行侧门禁。
- **结论**: 自然语言警告不能独自形成安全边界，外部数据必须与授权动作隔离。
- **结果**: 验收直接检查是否泄露提示、越权写文件或污染后续记忆，而不是让模型自报安全。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 要为 Agent 增加发信、付款、删数据、生产部署、数据库写入或跨租户读取能力。
2. 在“做成一个专用工具”与“写 Skill 后让 Agent 用 Shell/代码执行”之间选择。
3. 要接入 MCP、插件、第三方 API 或生成代码，并需要确定供应链、凭证和沙箱边界。
4. 工具数量、schema 或描述不断膨胀，模型开始误选或上下文成本过高。
5. 安全规则目前只存在于 Prompt、生成代码或最终输出过滤中，需要下沉为不可绕过的控制。

### 语言信号 (用户的话里出现这些就应激活)

- “这个能力应该做成 Skill 还是工具？” / “Skill or dedicated tool?”
- “怎么给 Agent 最小权限？” / “least privilege for the agent”
- “Shell、代码解释器或 MCP 安全吗？” / “sandbox / MCP trust boundary”
- “如何防止模型绕过权限或误操作？” / “prevent unsafe side effects”
- “工具太多，模型总是选错。” / “tool explosion / wrong tool selection”

### 与相邻 Skill 的区分

- 与 `formalize-and-verify-agent-work` 的区别: 本 skill 决定能力放在哪种接口及信任边界；后者把已明确的语义问题转换为可执行形式并验证计算结果。
- 与 `build-independent-review-loops` 的区别: 本 skill 优先用结构、权限和服务端真值预防越权；后者在仍需判断的候选动作或开放式产物上增加独立审核。
- 与 `engineer-agent-failure-closure` 的区别: 本 skill 主要做执行前的能力与权限设计；后者处理运行时已经发生的超时、失败、恢复与终止。

## E — 可执行步骤 (Execution)

当 skill 被激活后，agent 应按以下步骤执行：

1. **建立能力与资产清单**
   - 为每项能力记录读取的数据、可执行动作、凭证、租户范围、外部副作用、可逆性和失败代价。
   - 完成标准: 每个能力都有“最坏副作用”和“模型完成当前任务所需的最小权限”，没有未标注的外部访问。

2. **按风险选择表达形式**
   - 易变且以解释流程为主：Skill；低风险通用计算：受限代码执行器；结构复杂或高风险动作：专用工具；纯确定流程：普通程序或工作流。
   - 完成标准: 每项能力都有唯一主表达形式和选择理由，理由至少覆盖参数复杂度、变更频率、模型能力和风险。
   - 判停条件: 若任务完全确定、无须模型临场决策，停止 Agent 化设计，改用普通程序或工作流。

3. **画出不可绕过的信任边界**
   - 把认证、授权、租户过滤、业务真值、幂等、审批和最终写入放到模型、Skill 与生成代码均无法修改的层。
   - 完成标准: 对每个高风险动作，都能指出哪段非模型代码作最终裁决，以及拒绝时不会产生副作用。

4. **收窄并写清工具契约**
   - 定义使用时机、禁止场景、参数类型/单位/范围、返回状态、超时、幂等键、截断和错误语义；参数默认原样透传。
   - 完成标准: 契约同时含正例、反例和至少一个失败返回；模型所见调用与实际执行日志可逐字段对比。

5. **隔离执行与第三方供应链**
   - 对不可信代码限制文件、网络、进程、CPU、内存、时间和输出；对 MCP/插件审描述差异、固定版本、区分同名工具并使用最小凭证。
   - 完成标准: 沙箱不是 venv 或字符串黑名单；第三方更新不会绕过差异审查；凭证不能访问任务外资源。

6. **执行允许/拒绝双向测试**
   - 测试合法调用、越权调用、提示注入、参数静默转换、同名工具遮蔽、超时和不可逆动作确认。
   - 完成标准: 所有危险样本被不可绕过的边界阻止，所有应允许样本仍可完成；日志能复现裁决依据。
   - 判停条件: 若只能证明“拦截了坏请求”而不能证明“放行了合法请求”，不得宣布设计完成。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 任务是无敏感数据、无副作用的单次信息查询，增加专用工具和审批只会带来不必要复杂度。
- 需求和执行路径已经完全确定，传统程序或受限工作流更便宜、更易审计时，不要为了“Agent 化”引入模型。
- 问题只是某个已知工具实现 bug，且接口和信任边界已经正确；应直接修复和测试代码。

### 作者在书中警告的失败模式

- 用通用 Shell、浏览器或代码执行承担支付、删除、发信等高风险副作用，提示词无法成为最终权限边界（ce002）。
- 把第三方 MCP 元数据当可信配置，忽略描述投毒、静默升级、同名遮蔽和凭证外传（ce041）。
- 以 venv 或命令黑名单冒充系统沙箱，生成代码仍可访问宿主资源（ce044、ce047）。
- 检索后才做权限过滤，或把权限检查写在动态生成代码里，敏感信息和最终动作已越过信任边界（ce036、ce062）。
- 只写工具“能做什么”而不写触发条件、边界和参数语义；或包装层静默修改参数，模型无法诊断真实因果（ce039、ce040）。

### 作者的盲点 / 时代局限

- MCP、Agent Skills 与动态工具加载仍快速变化，具体 API 和产品行为不能替代稳定的最小权限原则。
- 全书偏软件工程和 Coding Agent；代码沙箱思路不能直接覆盖社会互动、隐性知识、物理操作和组织治理。
- 作者强调高风险长流程，低风险短任务采用完整 Harness 可能过度设计；应先比较更窄任务和传统软件方案。
- 供应链、合规审计、组织责任和长期维护成本的展开有限，正式上线仍需领域安全与法务评审。

### 容易混淆的邻近方法论

- 工具描述优化不能替代服务端授权；“模型更会调用”与“调用不可越权”是两个问题。
- 独立审核能降低误判，但不能替代最小权限、隔离执行和稳定数据层。
- 形式化规则有助于精确执行，但动态生成的规则或代码仍不能修改自己的权限和验证器。
