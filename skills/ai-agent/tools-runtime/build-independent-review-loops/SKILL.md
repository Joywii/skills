# 构建异源提议者-审核者闭环

## R — 原文 (Reading)

> 第一种机制是事前审批：在工具执行前，一个模型负责提议行动（Proposer） ，另一个独立的模型负责审查批准（Reviewer）——就像银行的经办、审核双签制度，转账指令须经两道签字才能生效。
>
> — 李博杰，第 4 章 4.5「执行工具」，PDF 第 118 页

---

## I — 方法论骨架 (Interpretation)

重复一次判断不等于独立验证；审核只有引入提议时不存在的新证据才增加可信度。
Proposer 负责生成候选动作或产物，Reviewer 负责对照约束与独立证据决定通过、退回或升级。
独立性可以来自另一模型家族、确定性执行器、环境最终状态、渲染截图、外部搜索或独立数据源。
安全 Reviewer 应只看完成判断所需的结构化动作和权限元数据，避免完整污染轨迹同时劫持执行者与门卫。
审核输出必须结构化到问题位置、证据、严重度、否决条件和可执行修复要求，而不是“看起来不错”。
退回后必须产生新候选、新证据和新审核记录；原样重试只会复制同一盲区。
循环要有最大轮数、时间或费用预算，超限后拒绝发布或转人工，不能无限争论。
审核者不能修改证据采集器、测试、发布门槛和稳定版本，否则独立审核会退化为自我批准。
通过只证明候选满足当前证据与门槛，不证明系统在所有下游任务上已提升。

## A1 — 书中的应用 (Past Application)

### 案例 1：Claude Code Sidecar 安全审查
- **问题**: 主模型可能被不可信内容影响，并在工具调用中发出危险动作。
- **方法论的使用**: Sidecar 轻量模型只读取工具名、解析参数和权限元数据，与主模型并行判断风险，对待审动作实施执行前门控。
- **结论**: 安全审查要与污染轨迹隔离，并在副作用发生前取得控制权。
- **结果**: 危险操作在批准前不会执行；简单风险分类可在数百毫秒完成，并行运行降低额外延迟。

### 案例 2：PPT 与讲解视频的异模态审核
- **问题**: Proposer 生成的 Slidev 代码语法正确，仍可能出现溢出、字体过小、图表不一致等视觉问题。
- **方法论的使用**: Reviewer 不复述代码解释，而是渲染每页截图，用视觉模型检查内容密度、可读性和布局，并把具体页码与修复条件退回。
- **结论**: 审核价值来自 Proposer 生成时看不到的渲染证据。
- **结果**: 验收覆盖论文贡献、图表一致性、无溢出及视频时长与语音同步，形成可迭代的质量闭环。

### 案例 3：Hermes 在外部审查下升级自己
- **问题**: Agent 能修改自身代码时，也可能降低测试门槛、破坏稳定版本或把合理提案误当能力提升。
- **方法论的使用**: Hermes 阅读原则并提交更新提案，由外部 Reviewer 审查；稳定版本、验收测试和批准门槛位于其修改权限之外。
- **结论**: 自我修改必须是“提案—外部审查—修复—再验证”，而不是直接覆盖生产版本。
- **结果**: 提案被接受只证明更新流程成立，书中明确不将其解释为下游能力已经提升。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 高风险工具动作需要在执行前审核，但人工逐次审批成本过高。
2. 代码、报告、PPT、视频、知识库变更等开放式产物无法由单一确定性检查完整验收。
3. 同一模型自检多次仍产生相关错误或虚假共识，需要引入异源证据。
4. Agent 要更新 Prompt、Skill、知识或自身 Harness，必须保护测试、发布门槛与稳定版本。
5. 现有 Reviewer 只说“通过/不通过”，没有证据、位置、修复条件和预算上限。

### 语言信号 (用户的话里出现这些就应激活)

- “让另一个 Agent 再审核一次。” / “add an independent reviewer”
- “同一个模型检查两次算双重验证吗？” / “is double-checking independent?”
- “怎么做 Proposer-Reviewer / Sidecar？”
- “审核总说没问题，但上线后还是错。” / “correlated reviewer errors”
- “自我修改怎么防止自我批准？” / “prevent self-approval”

### 与相邻 Skill 的区分

- 与 `design-trusted-agent-tools` 的区别: 本 skill 处理仍需判断的候选动作与开放式产物；工具设计 skill 先通过最小权限和稳定执行边界减少可发生的危险。
- 与 `build-reproducible-agent-evals` 的区别: 本 skill 是一次候选生成—审核—修复的运行闭环；后者建设跨任务、可重复、可统计的评估基础设施。
- 与 `attribute-first-errors` 的区别: 本 skill 在发布前查错并退回；后者针对已经发生的失败定位首个因果分叉并验证改进。
- 与 `formalize-and-verify-agent-work` 的区别: 能由确定性程序或约束裁决的输出优先形式化验证；本 Skill 只覆盖仍需异源语义判断的开放式或高风险残余。

## E — 可执行步骤 (Execution)

当 skill 被激活后，agent 应按以下步骤执行：

1. **定义候选与发布契约**
   - 写明 Proposer 输出格式、不可修改资产、硬性否决项、软质量维度和发布权限。
   - 完成标准: 每项标准可对应到可观察证据；测试、证据采集器、门槛和稳定版本不在 Proposer/Reviewer 修改权限内。

2. **为每项判断指定独立证据**
   - 优先使用测试、数据库状态、执行结果、渲染截图或外部事实；只有软质量才交给异源模型或人工。
   - 完成标准: Reviewer 至少拥有一种 Proposer 生成时不可见的信息；若没有，明确标记为“无独立验证”。
   - 判停条件: 若所有关键要求都能由确定性验证器直接判定，停止增加第二个 Agent，直接使用验证器门禁。

3. **隔离 Reviewer 输入和权限**
   - 安全审核只传结构化动作、目标、资源和权限元数据；内容审核传候选与必要证据，不默认传完整私有轨迹。
   - 完成标准: 能列出 Reviewer 每个输入字段的必要性；不可信自由文本被标记、限长且不能改变审核规则。

4. **固定结构化审核输出**
   - 输出 `decision`、`finding_id`、位置、证据、严重度、修复条件、置信度与是否需人工。
   - 完成标准: 每个 veto 都能转成一次局部修复；不存在只有形容词、无定位证据的退回意见。

5. **运行有界修复循环**
   - Proposer 根据 finding 生成新版本，重新执行/渲染取得新证据，再交 Reviewer；每轮保存 diff 和审核记录。
   - 完成标准: 每轮候选或证据至少一项发生变化；通过则携带证据原子发布，失败则保留最后版本和原因。
   - 判停条件: 达到最大轮数、费用、时间，或同一 finding 重复两次无进展时，停止自动循环并拒绝/转人工。

6. **校验审核系统本身**
   - 用已知好/坏样本测试 Reviewer 的放行、拦截和一致性，并检查模型家族、提示与数据源的相关性。
   - 完成标准: 误放与误拒均被报告；更换 Reviewer 或 Rubric 后重新校准，不能沿用旧分数自证有效。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 最终正确性可由一个稳定、低成本、确定性的验证器完全判断；此时第二个 Agent 只增加延迟与成本。
- Reviewer 无法获得任何新证据，只能读取与 Proposer 相同的输入并“再想一遍”；一致不构成验证。
- 低风险、可逆且人工目视即可立即确认的一次性任务，不值得建设持久多 Agent 循环。

### 作者在书中警告的失败模式

- Reviewer 与 Proposer 使用同模型、同提示、同输入或显著更弱能力，相关错误会制造虚假共识（ce045）。
- 安全 Sidecar 阅读被提示注入污染的完整轨迹，攻击可同时劫持执行者和审核者（ce046）。
- 审核循环无上限、拒绝后原样重试，系统持续消耗资源而没有新信息（PR-030、PR-043；ce005）。
- 审核者只看模型声明，不读取测试、渲染、数据库或真实环境状态，“通过”仍可能是假成功（ce055、ce065）。

### 作者的盲点 / 时代局限

- LLM-as-a-Judge、模型审核和自动归因可能共享同源偏差；即使流程可复现，也不保证结论与业务价值一致。
- 书中多用头部模型、视觉模型和自动验证器，中小团队未必承担多模型推理、金标校准和长期运维成本。
- 成功案例多于事故与长期维护数据，审核闭环的边际收益必须和传统人工审查、确定性软件比较。
- 对低风险短流程，复杂 Reviewer 架构可能过度设计；先证明独立证据带来的增益再扩展。

### 容易混淆的邻近方法论

- 多 Agent 数量不是独立性的代理；关键是信息来源、模型偏差、模态和权限是否真的不同。
- “审核通过”不是“能力提升”，后者仍需在独立评估集上比较新旧版本。
- 安全审核不能替代最小权限和服务端真值；Reviewer 漏检后的损害仍应被执行边界限制。
