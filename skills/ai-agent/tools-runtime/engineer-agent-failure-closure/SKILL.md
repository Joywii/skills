# 工程化 Agent 故障闭环

## R — 原文 (Reading)

> 检测靠“错误分类 + 模式识别” ，恢复靠“分级升级” ，终止靠“熔断器+ 全局上限 + 人工升级”——三者合起来， 就是Harness 对“Agent 可能永远跑下去”这个问题的完整回答。
>
> — 李博杰，第 5 章 5.1.5「故障与错误恢复」，PDF 第 148 页

---

## I — 方法论骨架 (Interpretation)

错误处理的边界不是一次请求，而是从检测到恢复再到终止的完整控制循环。
先判断故障属于瞬时、确定性、权限、参数、提交状态不明、上下文、异步还是控制流问题，再决定动作。
重试只有在故障前提可能改变时才有意义；相同输入、相同环境、相同错误的原样重放不是恢复。
含副作用的调用必须区分“响应失败”和“提交失败”，通过幂等键、状态查询或两阶段确认避免重复执行。
异步工具要把启动、pending、完成、取消和失败建模为不同状态，等待占位符不能冒充真实结果。
恢复动作应分级：短暂退避、修改输入、切换工具或策略、重建上下文、降级、人工接管。
系统要持续检测是否有真实进展；错误指纹或环境状态长期不变时必须熔断。
主任务、后台任务和每条恢复路径需要独立预算，防止辅助重试挤占核心配额。
终止必须是状态机的一等出口：验证成功、明确失败、预算耗尽、不可恢复或人工升级都应可达。
并行和多 Agent 系统还要把取消沿创建关系传播，并以“首个已验证成功”而非“首个声称成功”结算。

## A1 — 书中的应用 (Past Application)

### 案例 1：可打断异步邮件 Agent
- **问题**: 同步模型在长工具运行期间收到用户打断，容易把占位符当结果、忘记后台任务或漏处理批量事件。
- **方法论的使用**: 实验 4-5/4-6 引入事件队列、任务 ID、pending 占位符、进度查询、并行执行、取消、真实完成事件与恢复。
- **结论**: 异步不是把函数改成 async，而是显式管理部分完成状态和打断后的恢复路径。
- **结果**: Agent 能处理邮件事件；并行场景中会查询进度、取消慢任务，并在真实结果到达后整合其余任务。

### 案例 2：不可重试失败触发 Harness 修改
- **问题**: Agent 对参数或权限等确定性错误反复原样调用，形成无进展循环。
- **方法论的使用**: 实验 8-6 把重复错误归因到重试程序，允许 Agent 提出错误分类、重试与熔断补丁，但禁止修改验证器和稳定版本。
- **结论**: 可确定执行的恢复政策应进入程序，且修改本身也必须有失败轨迹重放和正常故障回归。
- **结果**: 验收同时要求不可重试错误不再循环、临时故障仍能正常恢复，避免“一律不重试”的过度修复。

### 案例 3：并行搜索的级联终止
- **问题**: 十个网站搜索 Agent 并行运行时，一处已找到答案，其余任务继续消耗浏览器与 token，且可能同时命中产生竞态。
- **方法论的使用**: Manager 监控结构化状态，以首个已验证命中原子结算，并向其余子 Agent 传播优雅取消和终止确认。
- **结论**: 成功也是一种终止事件；资源回收和取消传播属于故障闭环的一部分。
- **结果**: 图示案例从约 5 分钟串行搜索缩短到 19 秒，约 15 倍加速。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 工具超时、限流、断流或返回未知状态，团队不确定是否应该重试。
2. 订单、转账、发信、电话等动作可能已经成功，但客户端只看到超时或断线。
3. Agent 在同一错误和恢复动作间振荡、重复压缩、重复调用模型或无限委派子 Agent。
4. 异步工具、用户打断、批量事件和后台任务需要 pending、取消、恢复与优先级管理。
5. 并行任务需要在成功、失败、预算耗尽或父任务取消时可靠收尾并释放资源。

### 语言信号 (用户的话里出现这些就应激活)

- “这个错误该不该重试？” / “is this error retryable?”
- “接口超时了，但可能已经扣款。” / “unknown commit status / idempotency”
- “Agent 一直循环、一直调用同一个工具。” / “infinite loop / no progress”
- “怎么加熔断、预算和人工接管？” / “circuit breaker / retry budget / escalation”
- “异步任务如何取消和恢复？” / “pending task / cancellation propagation”

### 与相邻 Skill 的区分

- 与 `design-trusted-agent-tools` 的区别: 本 skill 处理工具运行后的失败语义、恢复和终止；前者决定工具在执行前应具备的最小权限与接口边界。
- 与 `attribute-first-errors` 的区别: 本 skill 构造在线运行时状态机；后者对已保存的失败轨迹做事后首错归因和配对改进。
- 与 `build-independent-review-loops` 的区别: 本 skill 关注故障是否可恢复和何时停止；审核闭环关注候选是否有独立证据可发布。
- 与 `distill-explicit-agent-state` 的区别: 状态蒸馏回答当前 pending、计数和锁是什么；本 Skill 定义失败事件触发的状态转移、恢复预算与终止出口。
- 与 `design-realtime-agent-interactions` 的区别: 本 Skill 是通用异步与恢复基础；后者仅在连续媒体、barge-in 和 partial/final 实时承诺中增加时序消费规则。

## E — 可执行步骤 (Execution)

当 skill 被激活后，agent 应按以下步骤执行：

1. **画出正常与异常状态机**
   - 至少包含 `ready/running/pending/succeeded/failed/cancelled/escalated`，并列出每条工具与上下文操作的状态转移。
   - 完成标准: 每个状态都有进入事件、允许动作和至少一个退出路径；不存在只能靠模型自由文本解释的隐含状态。

2. **建立错误分类与责任层**
   - 区分瞬时网络、限流、参数、权限、工具不存在、提交状态不明、格式/序列化、上下文、模型终止和控制流错误。
   - 完成标准: 每类错误绑定稳定错误码/指纹、是否可重试、责任组件和默认恢复策略。
   - 判停条件: 若无法区分“未提交”与“已提交但响应丢失”，禁止自动重放副作用，直接进入状态查询或人工核查。

3. **为每类错误设计改变前提的恢复动作**
   - 瞬时错误退避；参数错误修参；权限错误拒绝/升级；上下文错误重建；工具故障切换或降级；提交状态不明查询幂等状态。
   - 完成标准: 每次恢复都说明它改变了哪个失败前提；没有“所有错误重试 N 次”的通用分支。

4. **补齐幂等与异步语义**
   - 副作用动作使用业务幂等键、状态查询或预检/确认；异步接口拆为启动、查询、取消和完成事件，pending 携带任务 ID。
   - 完成标准: 重复请求不会产生第二次副作用；模型无法把 pending 占位符解析成业务结果；取消后有最终确认。

5. **添加进展检测、熔断和预算隔离**
   - 比较错误指纹、调用参数、产物 diff 和环境状态；为主链路、后台任务、每条恢复路径分别设次数、时间、token 与费用上限。
   - 完成标准: 连续无进展会进入熔断；辅助任务无法耗尽主任务配额；所有上限触发后都有确定性出口。

6. **定义结算、取消传播与人工接管**
   - 成功需外部验证；父任务结束向所有后代传播取消；保留未完成状态、最后证据和可恢复检查点。
   - 完成标准: 系统中无孤儿任务；“首个成功”是原子、已验证结算；人工接管能看见目标、状态、已尝试恢复和副作用记录。

7. **做故障注入验证**
   - 注入限流、断流、响应丢失、重复回调、参数错误、权限错误、假 pending、批量事件、取消竞态和恢复器自身失败。
   - 完成标准: 每个场景最终进入成功、明确失败、取消或升级；没有无限循环、重复副作用和资源泄漏。
   - 判停条件: 任一恢复路径可无限调用模型或工具时，不得进入生产。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 无副作用、成本极低、偶发且可人工立即重做的一次性任务，不必建设完整故障状态机。
- 根因已定位为一个确定性实现错误，修复并运行现有测试即可，不要用复杂重试掩盖 bug。
- 业务无法定义任何安全终止或人工升级责任人；此时应先补治理和所有权，而不是继续扩大自主性。

### 作者在书中警告的失败模式

- 非幂等动作超时后盲重试，第一次可能已成功，造成重复转账、订单、邮件或电话（ce048）。
- 参数、权限等确定性错误也原样重试，未改变故障前提（ce056）。
- 恢复路径无独立预算和熔断上限，曾出现连续失败三千余次的死亡螺旋（ce058）。
- 后台重试与主链路争夺同一配额，失败越多请求越多，形成重试放大（ce059）。
- 异步占位符被当成真实结果，或批量事件只处理最后一条（ce050、ce051）。
- Agent 自报完成、无进展检测或无停止条件，导致过早终止或无限运行（ce005、ce055）。

### 作者的盲点 / 时代局限

- 本书原则多来自高风险、长流程、异步 Agent；低风险短任务采用完整状态机可能成本过高。
- 许多案例依赖头部模型、事件运行时和较强运维能力，中小团队应先实现最小可靠闭环。
- 产品案例的长期事故率和维护成本披露有限，熔断阈值不能照搬书中数字，必须由本系统产线数据校准。
- 更原生的异步模型可能改变占位符等过渡实现，但幂等、取消、预算和终止语义仍需显式定义。

### 容易混淆的邻近方法论

- “重试次数”不是恢复策略；恢复必须改变输入、状态、工具或责任层。
- 首错归因解决“为什么失败”，故障闭环解决“运行时现在怎么办”，两者可组合但不可替代。
- 终止不是失败专属：已验证成功、人工取消和父任务结束同样需要可靠结算与资源回收。
