# 区分能力上限与连续可靠性

## R — 原文 (Reading)

> 前一个数字适合衡量探索时的能力天花板，后一个数字才接近支付、退款、权限变更、生产部署等场景的可靠性要求。
>
> — 李博杰，第 6 章 6.2.2「业务可靠性：关注 Pass^k」，PDF 第 173 页

---

## I — 方法论骨架 (Interpretation)

先区分问题是在问“多试几次能否至少成功一次”，还是“连续交付能否一次都不出错”。
Pass@k 把同一任务采样 k 次，只要至少一次通过就算成功，衡量带探索与筛选预算的能力上限。
Pass^k 要求连续 k 次全部通过，衡量稳定交付；安全、合规和幻觉等否决项不能被其他成功平均掉。
若单次独立成功率为 p，理想化下 Pass@k 为 `1-(1-p)^k`，Pass^k 为 `p^k`，两者随 k 朝相反方向变化。
独立同分布只是近似；共享缓存、环境漂移、顺序效应和自适应重试都会破坏简单公式，应优先报告实测序列。
必须写清 k 的统计单位：同一题多次采样、不同任务连续处理、同一用户长流程，含义不同。
探索任务可容许候选筛选，生产副作用任务还要披露重试成本、失败代价与是否可逆。
Pass@1 是两类指标的共同起点；没有单次基线，Pass@k 可能用大量重试掩盖脆弱系统。
指标只在任务通过标准、样本分布和否决项先定义后才有意义，并应配合样本量与不确定性报告。

## A1 — 书中的应用 (Past Application)

### 案例 1：单次成功率 60% 的相反结论
- **问题**: 同一个 60% 单次成功率，团队可能因多次尝试中几乎总能出现一次成功而误判为生产可靠。
- **方法论的使用**: 作者分别计算 `Pass@5 = 1-(1-0.6)^5` 与 `Pass^5 = 0.6^5`。
- **结论**: 前者约 99%，只说明允许五次探索时容易至少成功一次；后者约 7.8%，揭示连续五次都正确仍很难。
- **结果**: 书中据此把科研发现、漏洞挖掘、开放创作与支付、退款、权限变更、生产部署分配给不同指标。

### 案例 2：六类 Agent 基准的人类执行
- **问题**: 公开基准的整体分数无法说明任务是否可重复、通过标准是否合理，以及不同任务能否容忍多次采样。
- **方法论的使用**: 实验 6-2 要求设计者亲手完成 GAIA、AndroidWorld、SWE-Bench Verified、τ²-bench、Terminal-Bench 和 OSWorld-Verified 的不同难度任务。
- **结论**: 指标必须绑定任务语义、环境和人工可行性；探索型问答与真实状态变更不能共享默认 k 口径。
- **结果**: 实验产出人工执行记录与差异归因，用来校准任务难度和成功定义，而不是追求一个统一总分。

### 案例 3：四次自主科研仅一次完成
- **问题**: 自主科研系统偶尔走完整条流程，容易被展示为已经能够稳定科研。
- **方法论的使用**: 作者保留四次尝试的完整结果，而不是只展示唯一成功轨迹。
- **结论**: 一次成功可证明可行性上限，却不能证明连续可靠、结论真实或长期可进化。
- **结果**: 四次中三次在实现或评估阶段失败，只有一次走完全流程；失败与阴性结果被要求保留。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 模型或 Agent 报告 Pass@k 很高，团队要判断是否可以上线处理连续真实任务。
2. 科研、搜索、创作、漏洞挖掘允许多次候选，而支付、退款、部署等任务失败不可忽略。
3. 需要决定 k 的含义、重试预算、候选筛选成本和一票否决项。
4. 单次成功率看似不错，但长流程或连续多个账户的整体成功率快速下降。
5. 营销、论文或 benchmark 报告只给最好一次结果，需要还原系统真实稳定性。

### 语言信号 (用户的话里出现这些就应激活)

- “Pass@5 很高，能上线吗？” / “is high Pass@k production-ready?”
- “偶尔能成功和稳定成功怎么区分？” / “capability ceiling vs reliability”
- “连续十次都成功的概率是多少？” / “consecutive success / Pass^k”
- “这个任务应该看 Best@k 还是 Pass@1？”
- “重试几次后挑最好结果算可靠吗？” / “retry-and-select reliability”

### 与相邻 Skill 的区分

- 与 `build-reproducible-agent-evals` 的区别: 本 skill 选择和解释能力/可靠性指标；后者建设产生可信指标所需的数据集、重置环境、工具、协议和验证器。
- 与 `attribute-first-errors` 的区别: 本 skill 判断系统表现的统计口径；首错归因在失败样本内部寻找可修复的因果分叉。
- 与 `engineer-agent-failure-closure` 的区别: 本 skill 评估连续成功；故障闭环设计在线重试、幂等、取消与终止语义。

## E — 可执行步骤 (Execution)

当 skill 被激活后，agent 应按以下步骤执行：

1. **定义通过与否决项**
   - 写明真实环境结果、必要输出、路径限制、安全/合规/幻觉 veto，以及部分成功是否算通过。
   - 完成标准: 任意一次运行都能得到确定的 pass/fail 或预先定义的连续得分，且否决项不可被平均分抵消。
   - 判停条件: 若“通过”仍由主观印象决定，先构建 Rubric 或验证器，暂不计算 Pass 指标。

2. **确定业务问题和 k 的单位**
   - 标注是同一任务 k 次独立采样、k 个连续生产任务、单用户 k 步流程，还是 k 个候选中人工挑选。
   - 完成标准: 报告能用一句话回答“谁在什么分布上连续/重复了 k 次，以及失败代价是什么”。

3. **收集 Pass@1 基线与依赖信息**
   - 在代表性任务、多个固定种子和可重置环境中运行，记录每次结果、顺序、重试、成本和共享状态。
   - 完成标准: 有样本量、任务分层、均值与波动；若观察到顺序/共享状态影响，明确标记非独立。

4. **同时计算探索与可靠性指标**
   - 探索报告 Pass@k/Best@k；生产报告实测连续通过率或 Pass^k；同时保留 Pass@1、失败率与 veto 率。
   - 完成标准: 两类指标使用同一基础通过定义；不只展示对自己有利的一侧。

5. **把成本和风险放回解释**
   - 披露 k 次采样的 token、时间、人工筛选、重复副作用和失败损失；高风险场景按最坏失败而非平均收益决策。
   - 完成标准: 指标结论含适用场景、允许重试条件和不可接受失败，不能只给百分比。

6. **用阈值作决策并复测**
   - 探索任务设可行性/候选预算阈值；生产任务设 Pass@1、连续可靠性与 veto 上限，并在任务分布变化后重测。
   - 完成标准: 明确达到/未达到哪条门槛；样本不足时只支持“继续扩大实验”，不支持上线结论。
   - 判停条件: 若置信范围跨过决策阈值或关键任务样本不足，停止宣布优劣，补样本或降低结论范围。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 还没有可复现的任务、明确通过标准和真实环境验证；先建设评估基础设施。
- 目标是对一个具体失败做根因分析；聚合指标不会告诉你首个错误发生在哪里。
- 纯开放审美任务没有可操作 Rubric，强行二元化只会奖励肤浅代理指标。

### 作者在书中警告的失败模式

- 用 Pass@k 宣称生产可靠，把多次尝试最好结果当成每次都能交付（ce064）。
- 小样本单次运行或定向子集 4/4 就宣布整体 100%，忽略方差和任务覆盖（ce070）。
- 只优化计划长度、步数或 token 等机制指标，端到端成功、成本和风险反而恶化（ce072）。
- 只看总分，低频但严重的安全失败簇被大量简单成功样本掩盖（ce071）。

### 作者的盲点 / 时代局限

- 书中模型与产品数字处于 2025-2026 快速变化期，具体百分比只能说明机制，不能当长期基准。
- 独立试验公式在共享上下文、缓存、在线学习和环境漂移下可能失效，应优先实测真实序列。
- 对法律、医疗、金融等罕见灾难风险，Pass^k 仍不足以替代风险分析、合规门禁和事故建模。
- 中小团队可能没有足够任务和预算估计极高可靠性，必须诚实报告不确定性，不能用公式制造精度幻觉。

### 容易混淆的邻近方法论

- Pass@k 是“至少一次成功”，不是“平均 k 次成功率”，也不是连续通过率。
- Pass^k 不是简单把 k 设得越大越好；k 必须对应真实业务连续性和依赖结构。
- 高可靠指标不能替代过程安全：系统可能连续达成结果，却每次都走违规捷径。
