# 信息增量优先的多 Agent 协作设计

## R — 原文 (Reading)

> 核心判据只有一条：协作过程是否引入了单个 Agent 在生成时无法获得的新信息？

来源：第 10 章 10.2 “多 Agent 何时真正优于单 Agent”，PDF 第 278 页。

## I — 内化 (Internalization)

多 Agent 的价值不来自角色数量，而来自信息集的变化。若多个实例看到相同文本、使用同类模型、按相同提示轮流改写，串行传递只会有损压缩；表面提升往往只是用了更多总 token。

有效增量通常来自四类：独立观测（不同网页、文件、模态、环境状态）、独立验证（隐藏测试、渲染、另一能力域）、隔离权限（裁判只见规则、执行者不能改验证器）、真正并行的外部结果（多个慢任务同时完成）。

先证明信息增量，再选上下文边界。共享上下文保留细节、通信简单，适合同一任务连续阶段；但会膨胀、继承锚点与角色惯性。隔离 Agent 能保护权限、减少噪声并提高独立性；代价是所有必要状态都必须放进自包含移交包。

拓扑应跟依赖图匹配：Manager 适合需要全局分解和汇总的任务，但会成为单点瓶颈；去中心化移交适合动态专业路由，但必须由运行时保存访问链、预算和循环检测；并行 fan-out 只用于依赖独立的子任务。

协作运行时还要治理共享状态、版本、取消树、deadline、幂等消息、写空间和语义合并。完成不能靠各 Agent 自报，而要由原始目标的外部验收统一裁决。

## A1 — 作者案例 (Author's Cases)

### 案例 1：提议者-审核者引入渲染新模态

- **问题**：同一模型再读一遍文本，为什么仍看不出 PPT 溢出或视频成片问题？
- **方法**：实验 5-4/5-5 让提议者生成产物，审核者查看真实渲染截图/视频结果，而非只读生成源文本。
- **结论**：审核有效是因为加入了提议时不可见的新模态和执行结果，不是因为多一个角色名。
- **结果边界**：若审核者与提议者共享模型、提示和输入，仍可能共享盲区。

### 案例 2：独立网页任务并行

- **问题**：跨设备或多网站收集/填表怎样缩短总等待时间？
- **方法**：实验 10-3 让手机与电脑 Agent 独立 ReAct 并结构化通信；实验 10-4 由 Manager 分派 10 个网站、消息总线汇总并级联终止。
- **结论**：独立外部状态允许真并行；示例从约 5 分钟降至 19 秒，约 15 倍，同时暴露竞争和取消治理需求。
- **结果边界**：这是特定样例而非普遍加速定律；协调、限流和共享状态可能消耗全部收益。

### 案例 3：狼人杀的信息与权限隔离

- **问题**：不同角色若看到全部信息，如何避免泄漏并保持裁决可信？
- **方法**：实验 10-6 使用代码裁判和受限上下文，只向每个 Agent 暴露其角色允许的信息。
- **结论**：多 Agent 可以通过隔离信息和权限实现单一共享上下文无法表达的制度边界。
- **结果边界**：游戏机制案例证明隔离方式，不直接代表生产安全；真实系统仍需权限与审计基础设施。

## A2 — 适用场景 (Application)

### 何时调用

1. 决定单 Agent、共享上下文角色切换、Manager-worker 或去中心化多 Agent。
2. 任务包含不同网页/设备/模态/权限域，或多个慢外部调用可真并行。
3. 需要独立 proposer-reviewer、执行-裁判、研究-实现等验证闭环。
4. 多 Agent 已出现上下文膨胀、交接丢信息、循环委派、孤儿任务、文件冲突或错误级联。
5. 收到 “should we use multi-agent?”, “manager vs decentralized agents”, “shared context vs isolated agents”, “multi-agent handoff protocol”, “parallel agent orchestration”等英文请求。

### 语言信号

- 中文：“要不要拆多个 Agent”“主 Agent 怎么分任务”“审核 Agent 有用吗”“共享上下文还是隔离”“子 Agent 交接什么”“并行写文件冲突”。
- English: “does debate add value?”, “independent reviewer”, “fan-out/fan-in”, “agent delegation package”, “cascading cancellation”, “orphan agents”, “multi-agent information gain”.

### 与相邻 Skill 的区分

- `build-independent-review-loops` 聚焦提议-独立审核的验证结构；本 Skill 先判断是否存在信息增量，并覆盖并行、权限、通信和拓扑全局设计。
- `design-realtime-agent-interactions` 处理同一交互流的异步事件与取消；本 Skill 处理多个自治执行单元的上下文、所有权和协作拓扑。
- `formalize-and-verify-agent-work` 定义外部完成验收；本 Skill 确保各子任务的产物最终回到同一原始目标验收。
- `design-trusted-agent-tools` 管工具契约与权限；本 Skill 决定权限是否应通过 Agent 隔离，并治理跨 Agent 共享资源。
- `choose-agent-autonomy` 先证明动态自治优于单调用或固定工作流；本 Skill 只在此前提成立后判断多个自治单元能否带来信息增量。
- `isolate-before-compressing-context` 定义自包含隔离和保真移交；本 Skill 将其用于角色上下文边界，但不负责通用压缩策略。
- `engineer-agent-failure-closure` 定义幂等、取消传播和有限恢复；本 Skill 将其扩展到父子生命周期、移交循环与孤儿 Agent。

## E — 执行步骤 (Execution)

### 1. 建立单 Agent 等预算基线

固定模型、工具、总 token/时间/费用和验收集，运行单 Agent 或确定性工作流；记录成功率、延迟、成本和失败类型。

- **完成标准**：有可重复的基线，且与候选多 Agent 使用相同总预算或明确报告额外预算。
- **判停点**：任务固定可枚举或单 Agent 已达验收且多 Agent 只增加复杂度时，停止拆分。

### 2. 为每个候选角色证明信息增量

填写 `new_observation / independent_verification / isolated_permission / parallel_external_result` 四列，指出该角色在生成时新增了什么，而非只写“更专业”。

- **完成标准**：每个 Agent 至少有一项可验证增量，并能构造去掉它后的消融预期。
- **判停点**：所有 Agent 只看相同输入、使用相同能力并串行改写时，退回单 Agent或增加一次独立工具验证。

### 3. 从依赖图选择拓扑

画子任务 DAG：有全局分解和统一汇总用 Manager；动态专业路由可去中心化；互不依赖的外部任务 fan-out；强顺序任务不伪并行。

- **完成标准**：每条边标明输入、产物、所有者和验收；拓扑无未处理环，关键路径与预期加速可计算。
- **判停点**：子任务边界只能由共享隐含上下文解释，或 Manager 无能力验证分解时，不启动并行。

### 4. 选择共享或隔离上下文

共享仅保留必要任务状态、证据和产物；需要独立审核、最小权限或噪声隔离时使用独立 Agent。为隔离任务准备自包含输入。

- **完成标准**：每项信息都有可见性等级，任何 Agent 只能看到其任务与权限所需内容；隔离 Agent 不需猜测父上下文。
- **判停点**：审核者继承提议者全部锚点而没有新证据，或隔离 Agent 缺目标/约束/验收时，重设边界。

### 5. 定义结构化移交包

移交至少包含 task_id、目标与完成标准、已确认事实与来源、约束/权限、输入/产物引用、预算/deadline、未决问题、置信度和输出 schema。

- **完成标准**：下游无需回看父对话即可开始；重复消息可幂等处理；任何结论能回到原始证据而非上游摘要。
- **判停点**：自由文本传话导致下游重问、重做或目标不一致时，暂停扩展拓扑并修协议。

### 6. 治理生命周期、预算和共享状态

运行时维护不可篡改的访问链、visited set、父子取消树、全局并发/深度/token/费用预算；写操作使用独立工作区、版本检查和合并验证。

- **完成标准**：取消父任务会清理全部后代；循环移交被拒绝；子预算从父预算扣减；并行写入不会静默覆盖。
- **判停点**：出现孤儿 Agent、预算指数增长、同一 task_id 回到已访问 Agent 或后写覆盖时立即终止任务。

### 7. 独立汇总与等预算验收

由不依赖子 Agent 自报的验证器检查原始目标，合并时保留异议和不确定性；与单 Agent 基线比较质量、尾延迟、成本、协调 token 和故障率。

- **完成标准**：多 Agent 在预设主指标上达到最小净收益，新增信息可以从消融解释，且安全/一致性/成本门全部通过。
- **判停点**：收益只来自更多 token、移除某角色无影响、协调成本抵消并行，或错误随链路放大时回退更简单拓扑。

## B — 边界与禁区 (Boundary)

### 不要在以下情况使用

- 多个角色看到相同输入、同一模型互相辩论，却没有新观测、工具、权限或验证信息。
- 步骤固定、结果确定且普通并发程序可以完成：用工作流/队列，不用自治 Agent。
- 无法提供结构化交接、总预算、取消传播、独立验收或写隔离：不要开放递归委派。
- 只是单 Agent 内部的不同提示阶段：称为共享上下文工作流，不虚增为多 Agent 架构。

### 明确反例与警告

- **ce025 非自包含委派**：隔离子任务只给依赖隐含历史的一句话，必然缺目标、约束和验收。
- **ce045 同源审核盲区**：Reviewer 没有独立模型、模态、执行或测试信息，只会制造虚假共识。
- **ce055 自报完成**：各子 Agent 说完成不能替代原始目标的统一外部验收。
- **ce105 同信息堆实例** 与 **ce106 共享上下文惯性** 约束拆分前的信息增量和共享边界。
- **ce107-ce114** 覆盖自由文本交接、文件权限混置、孤儿 Agent、Manager 单点、移交循环、并发覆盖、错误级联与递归预算爆炸；这些都必须由运行时而非提示词约束。

### 阶段 0 批判边界

- “信息增量”在设计前并不总能精确估计，相关模型仍可能共享偏差；必须用等预算单 Agent 对照和角色消融验证，而非理论自证。
- 书中多 Agent 案例规模有限，19 秒对 5 分钟是特定并行样例，不代表一般任务存在 15 倍加速或质量提升。
- 2025-2026 年 A2A/MCP/Agent 运行时快速演化，具体通信协议和产品会变；结构化移交、最小权限、预算和外部验收仍需保留。
- 作者偏重长流程与复杂 Harness，容易让短、低风险任务过度多 Agent 化；强单模型、普通程序或确定性并发常是更便宜基线。
- 独立审核和隔离执行增加组织与算力成本，小团队若无法维护消息总线、权限和合并测试，应减少自治节点而不是把治理写进 Prompt。

## 相关 Skills

- `choose-agent-autonomy` 是前置：先排除单调用、确定性工作流和单 Agent 已足够的任务，再为确有动态性与信息增量的部分设计协作。
- `isolate-before-compressing-context` 是上下文前置：隔离输入必须自包含，移交必须保留目标、约束、证据与验收；隔离本身不等于需要多个自治 Agent。
- `build-independent-review-loops` 是审核前置：只有审核者获得异源证据时，Reviewer 角色才产生信息增量；同源互评不算协作收益。
- `engineer-agent-failure-closure` 是运行时前置：父子取消、幂等移交、有限恢复和终止出口必须先成立，再开放并行与递归委派。
